# Configuration & Environment Standard

> **Type:** Generic, reusable standard · **Version:** 1.0 (2026-07-17)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the engineering-standards library, bundled in the `standards` skill (references/).
>   Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs how configuration enters a system: env vars and boot validation, client-bundle
> exposure, environment gating, the config taxonomy, shared-constant endpoints, and
> build/runtime coupling. Core idea: **config is untyped input from your most trusted,
> least tested source — validate it once, at boot, and refuse to start wrong.**

---

## 0. Scope

Assumed context: a multi-repo TypeScript workspace — backend API, web client(s), mobile
app, worker(s) — with docs generated by wiki-system and client types code-generated from
a runtime API spec. Rules are stack-agnostic; technology names are labelled examples.

This standard owns: env var handling and boot validation, client-bundle exposure,
environment gating, the config-vs-constant taxonomy, single-source runtime config
endpoints, build/runtime coupling, `.env` hygiene. Not its lane:

- **Secret content** — strength, storage, rotation, transport → `security.md`.
- **Script vocabulary, lockfiles, CI-parity mechanics** → `tooling-and-workspace.md`.
- **The API spec source of truth and codegen workflow** → `api-contracts-and-codegen.md`.
- **Whether a config comment tells the truth** → the comment standard
  (`comment-standard.md`). This standard owns the *direction
  of derivation*: required-ness is defined by code; comments and docs follow it (§2.2).

## 1. Core principle

Every other input has a checker: request bodies get schemas, code gets a compiler.
Environment config has nothing unless you build it — `process.env` is a bag of
`string | undefined` that any typo satisfies. The Twelve-Factor App (Factor III, Config)
settled *where* config lives — the environment; the TypeScript ecosystem converged on
the missing half: **parse it, don't cast it** at startup, and exit before accepting
traffic (e.g. Zod-based env schemas, t3-env, envalid). Two consequences follow:

1. **The boot guard is config's type system.** A var is required, numeric, or an enum
   because the guard enforces it at boot — not because a doc says so.
2. **A misconfigured process must not run.** Every rule converts a silent runtime
   degradation (a breaker that never fires, prod in dev posture) into a loud refusal.

## 2. Fail-closed boot

### 2.1 One accessor, no scattered reads

All env reads go through **one module per deployable**, via a typed accessor that logs
the missing key and exits non-zero when a required var is unset. **NEVER** read
`process.env` raw from feature code: scattered reads surface a missing value at *first
use* — mid-request, hours after deploy — instead of at boot. In one audited four-repo
workspace the API reads all ~22 required vars through one accessor at import time; a
missing one prints a single lifecycle line and exits 1 before the server binds a port.
The refusal message MUST reach the console unconditionally — a dev-gated logger silent
in production eats exactly the message you need during a failed prod deploy.

### 2.2 Required-ness is defined by the boot guard

If the accessor exits when the var is unset, the var **is required** — whatever any
comment, wiki page, or deploy checklist claims. Docs, tests, and runbooks derive from
the guard, never the reverse. Incident shape: an audited env module said "optional at
boot" directly above a *required* accessor call — anyone deploying from the prose ships
a service that refuses to boot. Fixing the comment is the comment standard's lane; the
rule here: when guard and prose disagree, **the guard is the definition**.

### 2.3 Typed accessors — validate shape at boot, not at use

- **Numeric vars:** parse at boot; require finite and in-range. `Number(raw)` at the
  point of use is not validation — a non-numeric value becomes `NaN`, every comparison
  against `NaN` is false, and whatever the number gates **fails open with no error**.
  Audited example: a global daily send-cap breaker that would never trip against `NaN`.
- **Enum vars:** validate against the closed list; refuse anything else (§4).
- **URL vars:** normalize once at boot (scheme, trailing-slash policy) so no consumer
  re-implements the cleanup.
- **Secrets** may carry structural tripwires at boot — e.g. a minimum length catching
  truncation. A shape check, not an entropy guarantee; content rules → `security.md`.

### 2.4 Optional means "degrades", never "breaks"

A var may be optional **only** when unset produces a defined, safe degrade — with the
default stated explicitly at the read site, not implied by `|| fallback` at call sites.
Audited legitimate case: an auxiliary post-processor whose infrastructure pointers are
optional — unset, the system delivers the unprocessed artifact (documented at the
declaration) — while the same service's core storage vars stay required. The test:
**merely worse ⇒ optional with explicit default; broken or unsafe ⇒ required.**

## 3. No unsafe fallback defaults

Anything security- or money-relevant gets **no fallback**. Unset means refuse to boot —
never "assume something plausible":

- **NEVER** a default database/service URL — one bad deploy away from a test run
  pointing at production.
- **NEVER** a default secret or signing key — a known default is not a secret (content
  rules → `security.md`; the *no-default* rule is boot policy, so it lives here).
- **NEVER** an absent spend/rate cap defaulting to unlimited — a config mistake becomes
  an unbounded bill. Unset cap ⇒ refuse boot.
- Bootstrap credentials (seed admin) MUST refuse to seed when unset rather than fall
  back to a hardcoded credential — an audited boot seeder does exactly this.

For this class the only acceptable default is refusal. High consequence, high
plausibility — these are the vars most often "temporarily" defaulted during bring-up.

## 4. One canonical environment variable

- Exactly **one** var names the environment. Every env-gated behaviour — spec/docs
  surfaces, debug routes, rate limiting, cookie flags, CORS, proxy trust — keys off that
  var and nothing else. Two gates on two vars will eventually disagree.
- Its value is validated at boot against the **closed, enumerated list** of environments
  (recorded in Appendix A). Gates typically compare `=== 'production'`, so an
  unvalidated `prod` or `Production` passes every string check and boots production in
  **full dev posture** — rate limiting inert, spec UI and debug routes exposed,
  permissive CORS. Adding an environment is a deliberate enum change, not a string that
  appears in a deploy console.
- `NODE_ENV` is a **build flag, not your environment**. Toolchains set and override it —
  one audited mobile build system forces `NODE_ENV=production` on every build regardless
  of target — so gating on it means gating on your bundler's mood. Own your variable.
- Spec/docs surfaces (e.g. a served OpenAPI document) gate to non-production on this one
  var — mechanics in `api-contracts-and-codegen.md`.
- **"Not production" is not an auth model.** An environment gate reduces exposure; it
  authenticates nobody. Anything that must never run open (internal callbacks, admin
  surfaces) carries real auth in *every* environment → `security.md`.

## 5. Client-bundle exposure

- Only vars under the platform's **public prefix** (e.g. `NEXT_PUBLIC_*`,
  `EXPO_PUBLIC_*`) reach browser/mobile bundles. The prefix is a publishing decision:
  prefixed values are **inlined at build time** into an artifact you cannot recall.
- **A secret in a public-prefixed var is a leak the moment the build runs.** Renaming a
  server var into the public prefix "to make it work" is the classic path; the fix is a
  server-side proxy or endpoint, never the prefix.
- Every **new** public-prefixed var is an explicit review event: "is this value safe on
  every user's device, forever?" gets asked by a human, not implied by a green build.
- Inlining footgun: a changed public var needs a rebuild (often a cache clear) — hot
  reload keeps the stale value. Say so where the var is documented.
- Genuinely public, environment-invariant identifiers (e.g. OAuth client IDs) MAY be
  committed constants instead — env is for values that *vary by environment*.

## 6. The config taxonomy — every value has exactly one home

Most "should this be an env var?" arguments are a missing bin assignment. Three bins:

| Bin | What | Home | Why |
| --- | --- | --- | --- |
| **1. Externally-imposed constants** | Vendor/model caps, protocol limits — dictated by the outside world | **Code constants**, with the imposing source **named and dated** at the declaration | They change only when the outside world changes — a code change (and re-verification) anyway |
| **2. Product-editable values** | Prompt templates, copy, parameters a non-deploying human tunes | **Durable store** (DB) with an editing surface; code keeps only the first-boot seed | Editing must not require a deploy; a store can carry versioning and audit, which env vars cannot — the standing critique of env-only config, answered by relocating *editable* values |
| **3. Cross-client shared constants** | Validation caps, prices, defaults server and clients must agree on | A **single runtime config endpoint** (e.g. `GET /config`), consumed by **every** client, with per-constant fallback semantics | The repos share no build; hand-mirrored literals drift silently — the wire is the only enforceable common ground |

Rules on the bins:

- **Bin 1:** the declaration cites its source ("cap verified <date> against <vendor>'s
  API docs"). An unlabelled magic number cannot be re-verified and will be "fixed".
- **Bin 2:** apply the stored value at **consume time**, never baked into stored
  derivatives — otherwise an edit cannot take effect and stale copies ship forever.
- **Bin 3:** define per constant what a client does when the endpoint is unreachable —
  **stale-tolerant fallback** (a committed literal; fine for display), **hide until
  loaded** (anything money-adjacent), or **fail**. A committed fallback literal is a
  cross-repo mirror — pin it or declare it unpinned (comment standard §3.3), and list
  it in Appendix A.

### 6.1 Partial adoption is worse than none — a named failure

**A single-source mechanism that is only partially adopted is worse than no mechanism,
because it FEELS solved.** Audited shape: a config endpoint was built to serve the
constants clients had hand-mirrored — caps, prices, defaults. One client consumed it
*only for prices* while still validating forms against its own hardcoded caps; a second
client never called it at all. Every reviewer who saw the endpoint assumed the drift
class was closed; the dangerous mirrors were all still live behind the appearance of a
fix. **Adoption is part of the feature:** the migration is done when every client reads
the endpoint **and the hardcoded copies are deleted** (declared fallback literals
excepted). Until then, track the endpoint as unfinished, not shipped.

## 7. Adding a variable is a four-place change

Every new env var touches four places. Missing one is *the* standard config failure:

1. **The boot guard** — accessor call and typed export in the env module (§2).
2. **Every deploy environment's config.** Missed ⇒ that environment's next deploy
   refuses to boot — the guard *working*, but the process failure was this step.
3. **The test seed** — the suite's env setup seeds every boot-required var with inert
   dummy values so a clean checkout passes and no test reaches a real service. Missed ⇒
   CI fails at import on the guard. Hermeticity → `testing.md`.
4. **The manifest** — the docs contract page or `.env.example` enumerating the var (§9).
   Missed ⇒ the next person greps, and the manifest stops being trusted.

Make the four places a review item, not tribal knowledge. In a wiki-system project,
place 4 is the generated env contract page — refreshed via the wiki workflow.

## 8. Build/runtime coupling

- **Artifact contents pin the runtime.** The moment an artifact ships dependencies —
  `node_modules/`, native bindings, anything compiled — the build machine's CPU
  architecture and runtime version become part of the deploy contract. Incident,
  genericised: a backend artifact shipped `node_modules` with a native binding; CI built
  on x86_64 while the fleet ran ARM instances; every instance **crash-looped at boot**
  on a dynamic-library load error and forced a rollback — code and binding both correct,
  only the build machine wrong.
- **CI build env MUST match the deploy env** — architecture, OS family, runtime major —
  whenever compiled artifacts ship. Assert it in the build script; don't rely on memory.
  `engines` pinning and CI-parity mechanics → `tooling-and-workspace.md`.
- **Client bundles couple the other way:** public env is baked at build (§5), so a
  bundle built for one environment cannot be promoted to another unless every baked
  value is environment-invariant. Decide per client — *promote* artifacts (bake nothing
  environment-specific) or *build per environment* (never promote); deciding neither
  means someone ships a staging URL to production.

---

## 9. `.env` hygiene

- Local `.env*` files are **gitignored, always**. Deploy values live in the deploy
  platform's config, never in the repo (Twelve-Factor App, Factor III). Secret storage
  itself → `security.md`.
- **One maintained manifest** enumerates every var: a committed `.env.example` with no
  real values, or the docs contract page (§7 place 4). The env module is the ground
  truth; when they disagree, the module wins and the manifest is regenerated.
- **CI seeds its own env** from the repo's test setup (§7 place 3) — never a committed
  `.env`, never a copied production value.
- If clients load layered `.env` files (base → variant → local), document the precedence
  in the manifest — an override file that silently never loads is a real, audited failure.

## Failure shapes

Named patterns from real audits and incidents, genericised. Recognise → fix the class.

1. **The NaN fail-open** — a numeric var cast at use instead of parsed at boot;
   non-numeric ⇒ `NaN` ⇒ every comparison false ⇒ the cap it gates silently never fires.
2. **The typo'd environment** — the environment var compared but never enum-validated;
   `prod` boots production in dev posture: no rate limits, debug + spec surfaces open.
3. **The lying "optional"** — prose says optional, guard exits; a deploy planned from
   the prose doesn't boot. Required-ness flows from the guard (§2.2); fix the prose.
4. **The half-adopted config endpoint** — the endpoint serves the shared constants; one
   client still validates against its own hardcoded copy, another never calls it. The
   drift is intact and now *looks* solved (§6.1).
5. **The public-prefixed secret** — a server secret renamed into the public prefix to
   unblock a client build; shipped in the bundle, unrecallable, on the first build.
6. **The arch-mismatched artifact** — shipped native bindings built on the wrong CPU
   architecture; the fleet crash-loops at boot; rollback under pressure (§8).
7. **The three-place variable** — a new var misses the test seed (clean-checkout CI
   fails), a deploy environment (its next deploy refuses to boot), or the manifest (§7).
8. **The convenient default** — a security/money var with a plausible fallback (default
   DB URL, default secret, unlimited cap): "misconfigured" becomes "silently live" (§3).

## Checklist

Before merging config-touching work:

- [ ] Every new var reads through the env module's typed accessor — no raw `process.env`.
- [ ] Required vars refuse boot when unset; numerics finite and in-range at boot; enums
      validated against the closed list; URLs normalized once.
- [ ] Optional vars have an explicit, safe default at the read site — and the feature
      *degrades*, not breaks, without them.
- [ ] Nothing security- or money-relevant has a fallback default.
- [ ] Env-gated behaviour keys off the one canonical environment var, still enum-validated.
- [ ] No secret under a public prefix; every *new* public-prefixed var explicitly reviewed.
- [ ] Each new configurable value has a taxonomy bin (§6); if bin 3, every client
      consumes the endpoint and superseded hardcoded copies are deleted.
- [ ] All four places updated: boot guard, every deploy environment, test seed,
      manifest (§7) — and the Appendix A profile.
- [ ] If the artifact ships compiled deps: build arch/runtime still match the deploy
      target and the assertion still runs (§8).

## Guard rails

CI checks that make this standard enforceable rather than aspirational:

- **Lint-ban raw `process.env`** outside the env module(s) (e.g. an ESLint restriction
  with a path allowlist). Enforces §2.1 permanently.
- **Boot smoke test:** import (or start) the built entrypoint against exactly the
  manifest's var set — proves the manifest is complete *and* the guard passes with it.
- **Manifest sync check:** a test diffing the env module's accessor calls against the
  manifest's var list; fails on a var present in one and not the other.
- **Environment-enum test:** feed the boot guard an out-of-list environment value and
  assert refusal — pins §4 against a "temporary" third value appearing unvalidated.
- **Public-prefix allowlist:** CI fails when a public-prefixed var not in a committed,
  reviewed allowlist appears. Turns §5's review event into a gate.
- **Config-endpoint adoption pin:** a lint/grep gate fails when a literal copy of a
  served constant reappears outside its declared fallback site; clients type their
  consumption off the generated response schema (→ `api-contracts-and-codegen.md`).
- **Build-arch assertion:** the build fails when the CI machine's architecture differs
  from the declared deploy architecture while the artifact ships compiled deps.
- **Test-seed completeness is self-enforcing** — keep the suite importing the real env
  module so a new unseeded required var fails CI at import; never mock the module away.
