# AI Features Standard

> **Type:** Generic, reusable standard · **Rev:** 2 (2026-07-28)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
> Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs product features built on a language model — a chat surface, a retrieval-backed answer
> box, an assistant that calls tools on a user's behalf. Core idea: **model output is untrusted
> input that arrives from inside your own system**, so the trust boundary sits in the middle of
> your application rather than at its edge.

## 0. Scope

Applies whenever a language model's output reaches a user, a store, another service, or an
executable path — and whenever content the product did not author reaches a model's context
window. Assumed context: a multi-repo TypeScript workspace — backend API, web client(s), mobile
app, worker(s) — with docs generated by wiki-system and client types code-generated from the
running API's spec. Rules are stack-agnostic; tools and vendors are labelled examples. A project
shipping no model-backed surface never routes here.

**Owns:** instruction/data separation in context assembly; tool authority granted to a model;
validation of model output before use; AI-specific evaluation and reliability gates; model spend
and token caps; permission-scoped retrieval; AI disclosure and synthetic-media provenance.

**Does not own** (one-line cross-refs only):

- Using AI to write code, and model training or fine-tuning pipelines — outside the library.
- AuthN/Z, session tiers, secrets, rate limiting, SSRF → `security.md`; timeouts, retry policy,
  degradation ladders → `resilience.md`; idempotency and durable caps in the write filter →
  `data-integrity.md`; hermeticity and the unit/integration split → `testing.md`.
- Personal-data inventory, retention by class, deletion/export, third-party egress rows, residency
  → `data-protection.md`; masking mechanics → `observability.md`; wire envelope and error codes →
  `api-contracts-and-codegen.md`; provider keys and pins → `config-and-environment.md`.
- DOM sinks, sanitiser choice and CSP → `web-client.md`; `security.md` §7 owns XSS sink hygiene.
- Pinning/provenance of third-party **packages** and CI steps, and the waiver register every
  exception here uses → `supply-chain-and-build-integrity.md`.

**External anchors** — name + version + status, never URLs. *Anchors verified 2026-07-28;

## 1. Core principle — the boundary moved inside the process

Every other standard here guards a boundary you can point at: the network edge, a route, a bucket.
A model surface has a boundary with no edge to point at. Two moves create it:

1. **Content the product did not author enters the context** — a retrieved document, a fetched
   page, a user's message, a tool result, a prior turn. It arrives looking exactly like your own
   instructions, because to the model it *is* the same channel.
2. **Output leaves the model** — into a renderer, a database, an HTTP call, a tool invocation. It
   arrives looking exactly like your own service's output, because it came from your own process.

The instinct *this came from our own service, it is fine* is precisely backwards at both moves.
**Into the model, nothing you did not author may act as an instruction (§2, §3); out of the model,
nothing is used before it is parsed (§4).** The rest exists because the middle component is
non-deterministic, metered, and speaking to a person.

## 2. Instructions and data are separate channels

### 2.1 Content the product did not author is data, and never becomes instruction

Retrieved documents, fetched pages, uploaded files, tool results and user messages MUST enter the
context as **labelled, delimited data**, never concatenated into the instruction region. Assemble
context through one function taking typed segments — system, user, retrieved, tool-result — that
applies the delimiting; string concatenation at call sites is how an instruction region acquires a
caller nobody reviewed. This does not *stop* injection; it makes the intended instruction set fixed
and reviewable, so §2.2 and §3 have something to hold. That function's path is a profile row.

### 2.2 A turn processing untrusted content holds no authority to act for the user

A model invocation whose context contains content the product did not author MUST NOT hold tool
authority that changes state, spends money, or discloses data on the user's behalf — unless a human
confirms the specific action out-of-band (§3.3). This is the load-bearing rule of the standard: it
is the only one that still holds when injection succeeds. It prevents the confused deputy — a
document says "send the customer list to this address", the model has a send tool and the user's
authority, and the request is indistinguishable from the user asking. Split the work: an
untrusted-content turn returns *data*, a separate tool-bearing turn acts on it under §4.1.

### 2.3 Filtering is a layer, never the control

Input classifiers, injection-detection heuristics and output guards are **defence in depth** and
MUST be described as such in code and in review. No rule here may rest on a filter holding: the
attack surface is natural language, and no filter over it is complete. A design whose only injection
defence is a classifier has no injection defence — §2.2 and §3.2 bound the damage.

### 2.4 Nothing secret and no authorization decision lives in the system prompt

Treat the system prompt as disclosed. Keys, connection strings, internal pricing, unpublished policy
and other users' data MUST NOT appear in it, and no access decision may depend on the model
declining to act — authorization is enforced server-side in the tool (§3.2). Extraction by the model
is not the only path: in one audited multi-repo TypeScript workspace, an admin bundle served to
unauthenticated visitors shipped proprietary prompt text and internal pricing compiled into the
client (`security.md` §4). Prompts assembled in a client are public strings.

## 3. Tool authority and blast radius

### 3.1 Every tool is enumerated with its authority

Each tool a model can call is an API reachable by untrusted input, so the profile carries one row
per tool with all five columns filled: authority, scope, reversibility, confirmation requirement,
and blast radius with attacker-chosen arguments, stated concretely ("every row in one collection,
for any user"). **A tool whose blast-radius cell you cannot fill is an unfinished design, not a
documentation gap**, and a registered tool with no row is the finding — registries grow by
convenience and shrink never.

### 3.2 Least privilege per tool, enforced server-side, scoped to the acting user

A tool implementation MUST re-derive the caller's identity from the session and scope its query or
mutation by that identity — never from an id the model supplied as an argument. Grant each tool the
narrowest capability it needs (one collection, one bucket prefix, one verb), and grant an invocation
only the tools that turn needs. Two failures prevented: the tool honouring an id the model supplied,
and one over-broad "run a query" tool becoming the only capability an injection needs. Ambient
authority — a shared credential the tool layer holds regardless of caller — is the defect
`security.md` §6 and §9 ban, through a new door.

### 3.3 Irreversible, spending and disclosing actions require out-of-band confirmation

Actions that cannot be undone (delete, publish, send to a third party), that spend money, or that
disclose data beyond the acting user MUST be confirmed through a channel the model does not control
— a UI affirmation naming the concrete action and its arguments, never a model-authored summary and
never a model-emitted "the user approved" field. The confirmation MUST render the **validated tool
arguments** (§4.1), so an injected argument is visible to the human approving it.

### 3.4 A third-party tool or context server's responses are untrusted content

An externally hosted tool or context integration (e.g. an MCP-style server) both **receives your
prompt data and returns content into your context window** — a data egress and an injection vector
in one. Its responses MUST be treated as untrusted content under §2.1, it holds only the
least-privilege credential of §3.2, and it carries a profile row naming its operator and what is
sent to it. Pinning, provenance and adoption review are `supply-chain-and-build-integrity.md`'s
lane; the delta here is that its *response* gets no more trust than a fetched web page.

## 4. Model output is parsed, never trusted

### 4.1 Schema-validate every crossing, including tool-call arguments

Model output reaching a store, a service, a client or a tool MUST be parsed by a schema (e.g. Zod)
at that boundary, with per-field caps and closed enums — parse-don't-assert as `type-safety.md` §5
requires of wire input, applied to a source likelier than a network peer to produce a plausible
wrong shape. Tool-call arguments are the highest-value case: validate ids against the store's id
shape, reject unknown fields, range-check numerics — before the tool runs. A parse failure is an
expected outcome with defined behaviour (a bounded reformat retry or a typed error), never a 500
and never a cast.

### 4.2 Generated code, queries and commands are never executed without a sandbox

Model-produced code, SQL, shell, template expressions or filter objects MUST NOT be evaluated in the
application's process or against the production store. Where execution *is* the feature it runs in
an isolated sandbox — no network, no ambient credentials, CPU/memory/wall-clock bounds, allowlisted
filesystem, all four in the profile — and its result re-enters as untrusted content (§2.1).
Otherwise take structured parameters and build the query yourself: a validated `{ field, op, value }`
triple is a feature; a model-authored query string is RCE with a friendly face.

### 4.3 Model output is an attacker-influenceable source arriving at your sinks

`security.md` §7 and `web-client.md` §5.2/§5.3 own sink hygiene and scheme checks; the delta is that
model output *is* an untrusted source, which reviewers miss because the text looks like product
copy. Two consequences: **markdown rendering of model output is the sink most often missed**, and a
surface MUST NOT auto-fetch a URL the model chose — an image the model emits exfiltrates the
conversation through its query string before anyone clicks anything.

### 4.4 Grounded claims are verified against what was actually retrieved

Where a surface presents answers as grounded in sources, every citation the model emits MUST be
resolved against the retrieved set and dropped or flagged when it does not resolve — otherwise an
invented identifier renders as a real, clickable source, converting a fabrication into an
authoritative-looking one. Where retrieval returns nothing above threshold, the surface says so
rather than answering unsourced (`observability.md` owns that rate's visibility).

## 5. Non-determinism, evaluation and the CI gate

`testing.md` owns hermeticity, the unit/integration split and coverage; this section states only
what is AI-specific. Model calls are mocked at the process boundary in ordinary suites
(`testing.md` §4.3) — a unit suite that calls a provider is neither hermetic nor affordable.

### 5.1 Assert deterministically everything that is not the prose

Most of an AI feature is deterministic and MUST be tested as such, against recorded or synthetic
model responses: schema conformance and parse-failure handling (§4.1); tool-call and argument
validation; refusal rendering; untrusted content landing in the data region (§2.1); no tool-bearing
turn built for untrusted content (§2.2); caps firing (§6); the disclosure rendering (§9.1). Only
the prose needs an eval set — treating the whole feature as untestable ships the rest untested.

### 5.2 The prompt and tool surface is gated by an eval set

Prompts, context-assembly code, tool definitions and the pinned model version are **behavioural
source**: changing any of them changes product behaviour with no type error and no failing unit
test. Each MUST be version-controlled and gated by an eval set — a fixed corpus with programmatic
graders, growing by a case per defect — run against a recorded threshold a regression fails, with
adversarial cases in it (injected instructions inside retrieved content and in tool responses,
attempts to induce an out-of-scope tool call). The suite calls a real provider, so it is
**non-hermetic and paid**: it lives behind its own script, never inside `test`, declared per
`testing.md` §2.4, at a **cadence the profile records** — per-PR on the triggering paths, nightly,
or pre-release. Provider unavailability is infrastructure, never an eval regression.

### 5.3 Reliability is measured all-of-k, not any-of-k

For binary pass/fail cases, a non-deterministic component's success rate MUST be measured by
running each case **k times and counting it as passing only if all k runs pass**, with **k ≥ 3**
recorded in the profile — all-of-1 is any-of-1 wearing the rule's name. Any-of-k, the habit of
re-running until green, reports a number no user experiences, because a user gets one sample.
Graded cases, scoring a range rather than pass/fail, take a threshold on the mean **plus a floor on
the worst of the k runs** — a mean alone hides the sample a user actually got.

### 5.4 The model version is pinned, and moving the pin is a code change

Invocations MUST name an explicit, pinned model version rather than a floating alias, with the pin
in configuration (`config-and-environment.md`). Moving it is a diff that runs the eval set
(§5.2) — a silently updated alias is a production behaviour change with no author, landing on
prompts tuned against the previous version.

## 6. Cost and quota — every call is a paid external call

### 6.1 A durable cap, keyed to the strongest available principal, checked before the call

`data-integrity.md` §9 owns cap-inside-the-write-filter and `security.md` §8 owns durable per-user
spend caps and limiter placement. AI-specific: **tokens are a second cap dimension alongside
requests**, and the check happens *before* the paid call rather than after the response is metered
— a cap enforced on the way out has already spent the money. Where no authenticated user exists (a
public demo or widget — the highest-risk denial-of-wallet shape), the cap keys to the strongest
principal available — user, session, resolved client IP — **and a global per-surface ceiling always
exists**, because every key above the user is forgeable. The cap's principal is a profile row.

### 6.2 Token budgets are bounded at both ends

Every invocation MUST cap input tokens (truncating or refusing oversized context deterministically
and visibly, never silently dropping the middle) and output tokens: context growing with
conversation length or retrieval depth is an unbounded cost curve nobody chose. Agentic loops carry
a **step cap** — maximum tool iterations per request — because a loop with no step bound is
unbounded spend with a plausible reason for each step.

### 6.3 A retry loop around a paid call is a spend amplifier

Retry policy is `resilience.md`'s lane; dedup-on-retry is `data-integrity.md`'s. AI-specific:
retries and reformat loops (§4.1) count against the same budget as first attempts, and a provider
call that timed out is assumed **billed** unless the provider's documented behaviour states
otherwise. This does not contradict `resilience.md` §3.2's transient-by-default classification:
that rule governs whether the *work* is abandoned, this one whether the *provider is re-called* —
assume the spend happened, and re-call only where the result is still needed. Client-side
auto-retry needs an explicit attempt cap, or a user holding a key repeat becomes a spend event.

## 7. Latency, streaming and partial responses

`resilience.md` owns the timeout ladder, budget propagation and degradation rungs. AI-specific:

### 7.1 Streams need an idle deadline, not only a total one

A streamed completion MUST carry both a total deadline and an **inter-token idle timeout** — a
mid-stream stall presents as a healthy open connection and outlives any timeout that only measures
connect time. Cancellation MUST propagate to the provider on client disconnect, or an abandoned
page generates billed tokens nobody reads.

### 7.2 A partial response is not a result

Text received before a stream failed MUST NOT be persisted, parsed as a complete structure, or
handed to a tool as though the turn completed. A truncated JSON object that happens to parse is the
dangerous case: mark completion explicitly from the provider's finish signal, and treat truncation
as a defined outcome — retry within budget, or a typed degraded result the user can see — never as
success.

## 8. What leaves your boundary

### 8.1 Minimise what enters the prompt

Sending data to a model provider is a **disclosure to a third party**, made per field, not per
feature — `data-protection.md` §6.1 owns collect-only-what-is-needed, `data-protection.md` §5.2
owns per-field egress. The AI-specific rule: where retrieval assembles the context, the retrieval
query MUST be scoped by the acting user's permissions *before* embedding or ranking, so the model
is never handed a document the requester could not read — a permission check applied only to the
rendered answer leaks through summarisation.

### 8.2 Prompts and completions are payloads, not debug strings

Prompt and completion logging MUST follow the masking, bounding and retention rules any other
payload gets (`observability.md` §6.1, §6.2) — a full-prompt debug log is the highest-density PII
store the product has. Where transcripts are retained as a product feature they are a store like
any other: inventory row and deletion cascade are `data-protection.md` §2.1 and §4.1.

### 8.3 Training use of prompt content is recorded, not assumed

The provider's row in the third-party inventory (`data-protection.md` §5.1, §5.3) already carries
data classes, retention and deletion propagation. This standard adds **whether inputs may be used
for training**, and the fact that the payload is a *prompt* — so the data classes listed are
whatever context assembly (§2.1) puts in, not what the feature nominally handles. "We assumed zero
retention and no training" is the finding; a recorded value with the date checked is the answer that
makes §8.1 reviewable.

## 9. Disclosure and provenance

### 9.1 A model-driven interaction with a person is disclosed — and a test asserts it

**Applies when:** the profile records a surface where natural persons interact through a model; a
recorded "no natural-person interaction, because this is an internal ops tool" is a complete
answer. Where it applies, the product MUST disclose that the person is interacting with an AI
system, clearly and at first interaction, unless it is obvious from the context. The failure it
prevents: a person acts on model-authored advice — a support answer, a health or financial
suggestion — calibrating their trust to a human author who never existed. **A test MUST assert the
disclosure at every entry point the profile records**: one living only in a design file survives
exactly until a layout refactor.

### 9.2 Synthetic media carries provenance marking, and the marking is verified

**Applies when:** the profile records a surface that generates or materially manipulates audio,
image or video presented as authentic. That output MUST carry machine-readable provenance marking
(e.g. C2PA-style content credentials, or the format the profile records), applied in the generation
pipeline rather than at the edge, and **a test MUST read the marking back off a produced artifact**
— marking written but never verified is silently dropped by the first re-encode or storage
round-trip, and unmarked synthetic media is reused as evidence of something that never happened.
For generated **text**, the marking scheme is a profile row and a recorded "no interoperable scheme
for this medium, disclosure under §9.1 instead" is an answer.

### 9.3 Regulatory applicability is a profile row, never a verdict here

Whether an AI-specific regime binds this product — which obligations, from which date — is recorded
in the profile with the reason, the owner, and the date checked. **A recorded "no, because we ship
no EU-facing surface and no synthetic media" is a complete answer; an unrecorded answer is the
finding.** This file names the generic trigger and the testable rule (§9.1, §9.2) and states no
verdict about any organisation's obligations.

## Failure shapes — recognise one, cite it by name

- **The confused deputy with a mailbox.** A turn that reads untrusted content also holds a
  state-changing or sending tool under the user's authority; injected text in a retrieved document
  issues the instruction, indistinguishably from the user's own request, and the filter meant to
  catch it was the whole defence. Its reach is whatever the registry grew to: a tool added for one
  narrow workflow, holding a broad credential, with no stated blast radius. (§2.2, §2.3, §3.1, §3.2)
- **Green on the third run.** Evals are re-run until they pass and reported any-of-k, so a case
  succeeding 3 times in 5 counts as passing: a reliability no user experiences, and a prompt
  regression shipping behind a green gate. (§5.2, §5.3)
- **The denial-of-wallet loop.** A client auto-retries a timed-out completion with no attempt cap,
  against a surface whose cap assumed an authenticated user it does not have; every timed-out call
  was billed anyway, and one wedged page outspends the feature's revenue. (§6.1, §6.3)
- **The prompt log that became the PII store.** Prompts and completions logged verbatim during an
  incident — unmasked, unbounded, no retention — concentrating everything the feature was ever
  told about a person into one searchable index nobody inventoried. (§8.2)

## Checklist

Each box is diff-decidable unless marked *(judgement)* or *(gate status)*:

- [ ] New content source enters as delimited data through the assembly function, never concatenated into the instruction region?
- [ ] This turn sees untrusted content → it holds no state-changing, spending or disclosing tool without out-of-band confirmation?
- [ ] New/changed tool has a profile row with all five columns filled?
- [ ] New/changed tool re-derives identity from the session rather than a model-supplied id?
- [ ] Irreversible/spending/disclosing action confirmed out-of-band, showing the **validated** arguments?
- [ ] Model output crossing a boundary is schema-parsed, with defined parse-failure behaviour?
- [ ] Nothing generated (code, SQL, shell, template, filter object) is executed outside a sandbox?
- [ ] Rendered output is sink-safe, with no auto-fetch of a model-supplied URL?
- [ ] Prompt/context-assembly/tool-definition/model-pin change: eval set run, threshold met, reported all-of-k with k ≥ 3? *(gate status — one CI run answers all three)*
- [ ] Durable cap present, keyed to the recorded principal, with input/output and (if agentic) step caps?
- [ ] Streaming: idle deadline set, cancellation propagates, a truncated response is not treated as success?
- [ ] New prompt field is masked in logs and covered by a profile retention row?
- [ ] New prompt field is actually needed for the task? *(judgement)*
- [ ] Retrieval scoped by the requester's permissions before embedding or ranking?
- [ ] New entry point renders the AI disclosure, with a test asserting it? Generated media carries verified provenance?

## Guard rails

CI checks that make this enforceable rather than aspirational; judgement-only rules are named as
such. **Day-one rails** are cheap and land with the first model surface; the rest are earned at
scale. Every exception is a dated waiver with an expiry in the register the workspace already uses
(`supply-chain-and-build-integrity.md` §6.1) — never an AI-specific one.

- **[ai-features.GR1]** **Day one — dangerous-sink grep.** Fail the diff on `eval`-class calls, dynamic query
  construction, shell invocation and string-to-DOM injection; a human triages each hit against
  §4.2/§4.3. Reachability from a model result is not computable by grep, so the rail flags every
  site and the triage is the control.
- **[ai-features.GR2]** **Day one — budget, timeout and stream tests.** The durable cap rejects past budget under
  concurrent requests and under the unauthenticated principal; input/output/step caps are set on
  every path; a retry consumes budget (§6); a stalled stream trips the idle deadline, a disconnect
  propagates cancellation, a truncation yields a typed degraded outcome (§7).
- **[ai-features.GR3]** **Day one — tool-registry inventory check.** The code-side registry *exports* the tool list and a
  script asserts every exported tool has a profile row (§3.1) — driving it from the export rather
  than parsing Markdown survives a table reformat. Whether a blast radius is *acceptable* is
  judgement.
- **[ai-features.GR4]** **Schema-parse taint rule.** A taint-analysis rule (e.g. a Semgrep taint-mode rule) with the
  provider-client call sites named in the profile as **source** and store/HTTP/tool-handler entry
  as **sink**, failing any path that does not pass through a schema parse (§4.1).
- **[ai-features.GR5]** **Prompt-log scanner.** Extending the repo's secret/PII sweep: prompt and completion logging
  routes through the masking helper and a declared length bound; a direct logger call on a prompt
  or completion variable fails (§8.2).
- **[ai-features.GR6]** **Eval suite gate, at the profile's cadence.** The recorded threshold fails a regression (§5.2),
  reported all-of-k (§5.3), adversarial cases in the corpus. A same-input different-run flake is a
  finding, not a retry. This measures the layer; it does not prove the property — §2.2's
  architecture is the control.
- **[ai-features.GR7]** **Disclosure and provenance tests.** An integration test per recorded entry point asserts the
  disclosure renders (§9.1); a pipeline test reads provenance marking back off an artifact (§9.2).
- **[ai-features.GR8]** **Judgement-only, by design:** whether a capability *should* be exposed to a model at all (§3.3),
  and whether minimisation into a prompt went far enough (§8.1) — no tool decides these.
