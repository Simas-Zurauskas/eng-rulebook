# Type Safety Standard

> **Type:** Generic, reusable standard · **Rev:** 1 (2026-07-17)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
> Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs how TypeScript's guarantees are kept real: compiler strictness, the `any` and
> cast policy, schema-derived types, runtime parsing at trust boundaries, and discipline
> around generated types. The core idea: **the compiler only proves what you never
> assert** — every escape hatch converts a compile-time proof into a runtime hope.

---

## 0. Scope — when this standard applies

Assumed context (per the library's authoring contract): a multi-repo TypeScript workspace —
backend API, web client(s), mobile app, worker(s) — with client types code-generated from a
runtime API spec and docs generated by wiki-system. Everything here applies to any TypeScript
codebase; the multi-repo notes apply when there is more than one repo.

This standard owns: compiler flags, `any`/cast/non-null policy, runtime validation at trust
boundaries, schema-derived and single-source types, and how generated types are consumed.

It does NOT cover:

- What must be **tested**, including parser/contract tests → `testing.md`.
- The API spec as source of truth, the regeneration workflow, and generated-file CI checks
  → `api-contracts-and-codegen.md`.
- Env-var parsing at boot and config exposure → `config-and-environment.md`.
- Distributing one shared tsconfig/eslint base across repos → `tooling-and-workspace.md`.
- Reason strings on lint/compiler suppression directives → the comment standard
  (`comment-standard.md`, §3.1).

The bar is demonstrated, not aspirational: one audited four-repo TypeScript workspace held
**effectively zero `any` in product code** with `strict` on everywhere — three of four repos
scored 5/5 on type discipline. This codifies what made that true, and where it leaked.

## 1. Core principle

A static type is a **claim**. It is only worth anything if it was *proven* — by inference,
by a narrowing check the compiler verified, or by a runtime parse that rejected the
counterexamples. `any`, `as`, and `!` produce the same claims with no proof, and the
compiler then propagates the unproven claim as if it were true, silencing errors ever
further from the lie.

Two corollaries drive every rule below:

1. **Un-typed data exists only at the edges.** Inside the codebase, everything is typed by
   proof. At each trust boundary, data enters as `unknown` and is *parsed* into a type —
   never asserted into one.
2. **Every fact is written once.** A union, a cap, an enum, a wire shape has exactly one
   source; every other representation (DB schema, validator, spec, client type) is *derived*
   from it. Two hand-written copies of one fact is a drift bug with a fuse of unknown length.

## 2. Compiler baseline

### 2.1 Required flags

Every repo in the workspace MUST compile with `strict: true` **plus** the following flags,
which `strict` does not include. Each names the failure it prevents:

| Flag | Prevents |
| --- | --- |
| `noUncheckedIndexedAccess` | Trusting `arr[0]` / `record[key]` to exist. Indexing yields `T \| undefined`, forcing the missing-element branch — the classic "first issue of an empty list" crash. |
| `exactOptionalPropertyTypes` | Conflating *absent* with *explicitly `undefined`*. Load-bearing wherever PATCH semantics distinguish "don't touch" / "clear" / "set" — a real tri-state in audited update endpoints. |
| `noImplicitOverride` | A base-class rename silently detaching a subclass method that thought it was overriding. |
| `noFallthroughCasesInSwitch` | The missing `break` that runs two case bodies. |
| `noImplicitReturns` | A code path that falls off the end of a value-returning function, yielding `undefined` nobody typed. |
| `verbatimModuleSyntax` (implies `isolatedModules`) | Single-file transpilers (bundlers, test runners) mis-compiling type-only imports/exports that whole-program `tsc` handles. Forces `import type`, making erasure predictable. |

Anchors: the TypeScript 6.0+ generated `tsc --init` config ships `strict`,
`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`,
`isolatedModules`, and `skipLibCheck: true`, and offers `noImplicitReturns`,
`noImplicitOverride`, and `noFallthroughCasesInSwitch` as commented style options — this
baseline is upstream consensus, not house taste. Under 6.0 `strict` is also the compiler
default, so `"strict": false` is now an explicit opt-out someone has to write. See also the
Total TypeScript "TSConfig Cheat Sheet" and the TypeScript TSConfig Reference (both living
documents — §0).

A repo MAY adopt `exactOptionalPropertyTypes` or `noUncheckedIndexedAccess` in a staged
migration (they are the two high-friction flags on an existing codebase) — but a deviation
MUST be recorded in the project profile (Appendix A) with an exit plan, not silently omitted.

### 2.2 `skipLibCheck` stance

`skipLibCheck: true` is **permitted and is the default recommendation**: it skips checking
`.d.ts` files (mostly dependencies'), not your code; the errors it hides are usually
unfixable-from-here version mismatches; and the check-time cost of disabling it is large
(Total TypeScript's guidance). Still a deliberate trade — record it in the profile, and know
your own hand-written `.d.ts` files sit inside the blind spot.

### 2.3 One baseline, one standalone typecheck, per repo

- **Every repo runs the same flag baseline.** In a multi-repo workspace with no shared build,
  uniformity held only by hand *will* slip — extend one shared base tsconfig where possible
  (distribution mechanics → `tooling-and-workspace.md`). A framework-provided base config
  counts only if the §2.1 flags are verified present or added on top of it; "extends the
  framework base + `strict: true`" alone is not the baseline.
- **Every repo MUST have a standalone `tsc --noEmit` script, and CI MUST run it.**
  Framework-build-only typechecking is a drift vector: in the audited workspace, exactly one
  repo had no `tsc` script (typecheck happened only inside the framework's build) — and that
  was also the repo whose tooling had visibly slipped. A framework build can have its type
  errors toggled off by one config key, typically skips test files and scripts, and runs
  flags you don't control. The standalone script is the check you own.

## 3. `any` is banned

- **New code adds zero `any`** — explicit or implicit. `unknown` is the legal type for
  "I don't know yet": it is `any`'s safe dual, accepting anything but permitting nothing
  until narrowed.
- **Lint-enforce it**: `@typescript-eslint/no-explicit-any` at error, plus the
  `no-unsafe-*` family (`no-unsafe-assignment` / `-argument` / `-call` / `-member-access` /
  `-return`) so an `any` that sneaks in through a dependency cannot spread. All of these
  ship in typescript-eslint v8 `recommended-type-checked`; adopt that preset as the floor
  (`strict-type-checked` where the team accepts its documented semver instability).
- Why the family matters: one `any` poisons inference downstream — every touch point
  silently becomes `any` too. The ban is cheap to keep and expensive to regain.
- A third-party type forcing `any` on you is a boundary: wrap the call at one site, give the
  wrapper an honest type, and keep the `any` out of your code entirely.

## 4. Cast policy — every `as` is an unproven claim

`as` tells the compiler "trust me" and ends the conversation. Policy, in order of preference:

1. **Prefer proof**: control-flow narrowing (`typeof` / `instanceof` / `in` /
   discriminants), a user-defined type guard (`v is T`), or a runtime parse (§5).
2. **Prefer `satisfies` for conformance checks** — it validates a value against a type
   *without* changing or widening it, which is what most "annotate to be safe" casts
   actually wanted. `as const` is likewise not a cast; both are encouraged.
3. **A justified cast carries a one-line reason** on the same or preceding line — the same
   contract as lint-suppression directives (comment standard §3.1). A bare `as` with no
   provable justification is a review defect. Legitimate reasons are rare and real: a
   library's types lag its runtime, a proven-but-inexpressible invariant.
4. **`as unknown as X` (the double cast) is FORBIDDEN outside test files.** It can turn any
   type into any other and defeats even the checks `as` retains. In tests it is tolerated
   for building intentionally-invalid fixtures.
5. **Non-null `!` follows the same rules as `as`**: prefer a narrowing check; a justified
   `!` states why the value is provably present.

**The repeated cast is a missing helper.** If the same structural cast appears at two call
sites, stop: the second occurrence is the signal that a named type or typed helper is
missing. Canonical audit finding: `(err as { message?: string }).message ?? fallback`
hand-repeated at **~30 call sites across two client repos** — the *only* type-safety soft
spot in otherwise `any`-free code — with the ad-hoc shapes disagreeing field-by-field, even
though the HTTP client already normalized every rejection to one fixed shape. The fix is one
exported error type plus one `errorMessage(err: unknown, fallback: string): string` guard
helper — not thirty casts (§8).

## 5. Parse, don't assert — trust boundaries

A **trust boundary** is anywhere data enters the process from outside the compiler's view:
HTTP request and response bodies, env vars, queue/job payloads, webhook payloads, storage
reads (device storage, browser storage, files, schema-less DB fields), and cross-service
messages (e.g. push-notification payloads).

- **Every trust boundary MUST be runtime-validated with a schema, and the static type MUST
  be derived from that schema** (e.g. Zod and its `infer`) — one artifact yields both the
  runtime check and the compile-time type, so they cannot drift. `JSON.parse(x) as T`,
  `req.body as T`, and `process.env.X!` are assertions of exactly the facts a boundary
  cannot guarantee; the crash they defer surfaces far from the boundary, with a stack trace
  pointing at innocent code.
- **One validation mechanism per codebase.** Audited failure: internal job payloads
  validated by hand-rolled `isString` checks and conditional-spread reconstruction while
  every HTTP boundary used a schema library — two idioms, the hand-rolled one verbose and
  error-prone, and its output typed by a hand-written interface the checks didn't provably
  match. Internal boundaries (queues, workers) get the same schema treatment as HTTP.
- **Env vars are a boundary**: parse once at boot into a typed config object; the rest of
  the code imports the object, never `process.env` (boot-guard specifics →
  `config-and-environment.md`).
- **Wire-facing enums on a client come from the generated spec types, never a hand-written
  union.** A hand-written copy of a server enum compiles forever and drifts silently; the
  generated type moves when the server does, and the compiler reports the break. On the
  server, the enum's single source is a const array (§6) that feeds the spec.
- Validate at the boundary, then **trust inward** — do not re-validate the same data at
  every layer; that duplicates the schema and re-creates the two-sources problem (§6).

## 6. Single-source unions — DB, wire, and TS in lock-step

The strongest pattern the audit found, promoted here to a rule:

```ts
export const JOB_STATUSES = ['queued', 'running', 'done', 'failed'] as const;
export type JobStatus = (typeof JOB_STATUSES)[number];
```

- **Write the values once** as an `as const` array; **derive** the TS union from it; feed
  the *same array* to the DB schema's enum constraint, the runtime validator, and the API
  spec's enum. In the audited backend this kept DB, wire, and TS aligned **by
  construction** — a new status added to the array propagates to all three, and a status
  added anywhere else fails to compile or fails validation immediately.
- NEVER hand-write a union, DB enum, and spec enum as three parallel literals. Two of the
  three will outlive an edit to the third; nothing reports it.
- Apply the same discipline to closed key sets: derive lookup tables as
  `Record<JobStatus, Handler>` and give `switch`es over the union a `never`-typed default
  (or a `satisfies`-checked map) so adding a member breaks every site that must handle it.
- Which value crosses a repo seam, and via what contract, is owned by
  `api-contracts-and-codegen.md`; this section owns the in-repo derivation shape.

## 7. Generated types are build output

Client types generated from the running API spec are **artifacts, not source**:

- **NEVER hand-edit a generated file.** The next regeneration silently reverts the edit —
  the fix evaporates with no error. If the type is wrong, fix the spec and regenerate
  (workflow, triggers, and staleness CI → `api-contracts-and-codegen.md`).
- **Consume generated types through one facade module per repo** (e.g. an `api/types.ts`
  that re-exports the names the app uses). App code imports the facade and NEVER
  deep-imports the generated file. The audited client did this cleanly and it paid off
  twice: no hand-written contract types leaked into the app, and a regeneration that
  renamed internals broke one file, not fifty.
- **Never cite line numbers into a generated file** (in comments, docs, or reviews) — its
  lines shift on every regeneration. Reference exported symbol names.
- Generated files are excluded from lint/format and from `any`-counting (§3) — they are
  measured at their source, the spec.

## 8. Errors: `unknown` in, helpers out

- **Catch variables are `unknown`.** `strict` already enforces this via
  `useUnknownInCatchVariables` (TypeScript 4.4+, part of the `strict` family). The defect
  is un-doing it: `catch (e: any)` and an immediate inline cast are both §3/§4 violations.
- **Narrow through shared, typed helpers — not inline casts.** Each repo exports a small
  set of guard helpers, e.g. `errorMessage(err: unknown, fallback: string): string` built
  on `instanceof Error` plus a shape guard, and `isRecord(v: unknown): v is
  Record<string, unknown>`. Helpers use `v is T` signatures so the compiler participates;
  an inline cast is invisible to it.
- Where an HTTP client normalizes all rejections into one shape, **export that shape as a
  named type** and type every error callback with it. The ~30-site cast of §4 existed only
  because the normalized type was never exported — each call site re-guessed it.
- Record each repo's helper location in the project profile so agents find the helper
  instead of minting cast site #31.

## Failure shapes

Named patterns from real audits — recognize and name them in review:

1. **The thirty-site cast.** One structural cast copy-pasted at every call site, shapes
   drifting field-by-field, because a named type/helper was never exported. Fix the type
   once; delete the casts.
2. **The framework-build-only typecheck.** No standalone `tsc` script; the framework build
   is the only checker. One config key can disable it, test files escape it, and the repo's
   type health silently decouples from the workspace's. One repo in four had already slipped.
3. **The trusted boundary.** `JSON.parse(x) as T`, `req.body as T`, `process.env.X!` — an
   assertion where a parse belongs. The type lies from the first line, and the crash
   surfaces deep in innocent code.
4. **The hand-written twin.** A wire schema (or validator, or DB enum) hand-mirroring a
   type with nothing coupling them — e.g. spec component schemas hand-paralleling
   sanitizer outputs. Compiles forever; drifts into a wire bug the compiler cannot see.
   Fix by deriving both from one schema (§5/§6).
5. **The escape-hatch ratchet.** One `any` (often imported from a dependency) infecting
   downstream inference with the `no-unsafe-*` family off — each new usage site is silently
   untyped, and the blast radius grows until strictness cannot be re-enabled cheaply.
6. **The edited artifact.** A hand-fix inside a generated file, silently reverted by the
   next regeneration. The bug "comes back" with no diff anyone remembers making.

## Checklist

Before committing:

- [ ] Zero new `any` — explicit or via an unsafe operation the lint family would flag.
- [ ] Every new `as` / `!` carries a one-line reason; could it be narrowing, a guard, or
      `satisfies` instead? No `as unknown as` outside tests.
- [ ] Every value entering from outside (HTTP, env, queue, storage, webhook) is parsed by a
      schema, and the static type is derived from that schema.
- [ ] No union/enum written twice — `as const` source, everything else derived; switches
      over it are exhaustiveness-checked.
- [ ] Catch blocks keep `unknown` and narrow via the repo's shared helpers.
- [ ] Wire-facing enums/types on clients come from generated spec types via the facade —
      no deep imports, no hand-edits, no line-number citations into generated files.
- [ ] `tsc --noEmit` passes in every touched repo — run the script, not just the
      framework build.
- [ ] Any new tsconfig deviation is recorded in the project profile with a justification.

## Guard rails

CI checks that make this standard enforceable rather than aspirational:

- **[type-safety.GR1]** **Run each repo's standalone `tsc --noEmit` in CI**, as its own step, independent of the
  framework build. Fails shape 2 at the pull request instead of at the audit.
- **[type-safety.GR2]** **Lint at typescript-eslint v8 `recommended-type-checked` or above**, with
  `no-explicit-any` at error and the `no-unsafe-*` family enabled. Add
  `consistent-type-assertions` with object-literal assertions disallowed (kills
  `{} as T`, the emptiest claim of all) and `no-non-null-assertion` at warn or better.
- **[type-safety.GR3]** **Require reasons on suppressions**: `ban-ts-comment` configured to demand descriptions
  on `@ts-expect-error` (and forbid bare `@ts-ignore`); pair with the comment standard's
  directive-reason rule for `eslint-disable`.
- **[type-safety.GR4]** **Grep gate:** fail CI on `as unknown as` outside test globs. Trivial to run, catches the
  worst cast at zero cost.
- **[type-safety.GR5]** **Fail CI on a stale or hand-edited generated file** — regenerate and diff (owned by
  `api-contracts-and-codegen.md`; listed here because it is this standard's shape 6).
- **[type-safety.GR6]** **Share the tsconfig baseline** from one extended base file so per-repo drift is a diff,
  not a discovery (`tooling-and-workspace.md`).
