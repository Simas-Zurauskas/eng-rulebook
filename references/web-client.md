# Web Client Standard

> **Type:** Generic, reusable standard · **Rev:** 2 (2026-07-28)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
> Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs code shipped into an execution environment the attacker also controls.
> Core idea: **the browser runs your code and everyone else's in one origin, so every client-side
> control is a hint — the real ones live on the server or in a browser-enforced policy.**

## 0. Scope

Applies to the web client(s) in the assumed workspace shape: a multi-repo TypeScript workspace — backend API, web
client(s), mobile app, worker(s) — with docs generated by wiki-system and client types code-generated from the running
API's spec. Rules are stack-agnostic; frameworks appear as labelled examples. This is the browser-surface sibling of
`mobile-app.md`: a platform lane, not a second security standard.

**Owns:** refresh concurrency across a tab tree, sign-out teardown in a browser, route-guard semantics and bundle
contents, the enumerable holes in framework auto-escaping, URL-scheme and redirect checks, CSP *buildability*,
client-side CSRF applicability, third-party script admission and integrity, **accessibility of the rendered UI (this
file is the library's only accessibility lane)**, client error reporting, bundle staleness and build-inlined values.
**Does not own** (one-line cross-refs only):

- Session design and tiering; cookie attributes, the served header set, **and the token-storage and sink-hygiene
  rules themselves** → `security.md` §2, §7. Rotation, reuse detection, lineage revocation and the blip-vs-rejection
  rule → `security.md` §2.4. Dependency scanning and the privileged-origin *package* rule → `security.md` §10.
- Package admission and provenance, and **the waiver register** → `supply-chain-and-build-integrity.md` §6.1.
  Reporting mechanics, log hygiene, alarm classes → `observability.md` §7.3, §6.1, §3. Which env values may reach a

## 1. Core principle

Three facts about the browser that no server-side habit prepares you for:

1. **The origin is the unit of authority, not the module.** Your framework, an analytics snippet and a transitive
   dependency five levels deep all read the same DOM, cookies, in-memory token and keystrokes. There is no least
   privilege inside an origin; **admission is the only control** (§7).
2. **The client is the attacker's environment.** Every guard, flag and role check in the bundle is advisory: the user
   can edit it, and anything compiled in is published (§4). Client-side controls buy UX, never authorisation.
3. **The tab is not the session.** One session spans N tabs, each with its own JS heap, sharing one cookie jar and one
   server-side token lineage — so concurrency correctness is a browser-specific obligation (§3), and getting it wrong
   makes honest users look like thieves.

## 2. Session and token handling in a browser

**Applies when:** the client holds a bearer access token in JS memory and refreshes it from a cookie. Where a
back-end-for-frontend or a server-side session cookie authorises every request there is no token in JS: §2.1–§2.2 and
§3 do not apply and §6 stops being conditional. The profile records the shape per surface.

### 2.1 The token-in-memory rule, and the browser obligations that follow

`security.md` §7 owns the rule (memory only, never `localStorage`/`sessionStorage`). Its client-side consequences are
this file's: **persistence across reloads costs one refresh round trip, and that cost is the control**, and there is
**no developer-convenience exception**, because a "remember it locally" branch ships to production if it is in the
bundle at all (`config-and-environment.md` §5). Anchor honestly: ASVS 5.0 **14.3.3** bans sensitive data in browser
storage *with session tokens explicitly excepted*, so this standard is deliberately stricter than its anchor;
**14.3.1** (authenticated data cleared from client storage on termination) is what it does rest on.

### 2.2 Nothing security-relevant is derived from a client-decoded token

Decoding a token client-side for a display expiry or role is fine and labelled as such. The client MUST NOT treat a
claim as authorisation — a claim the client trusts is a role the user edits in devtools, OWASP Top 10:2025 A01 with
extra steps — and MUST NOT verify signatures client-side: the key is either public (proving nothing) or secret (and
now shipped to every visitor).

### 2.3 An authoritative rejection tears down client session state, not just the token

The zombie session named in `mobile-app.md` §2 arrives identically in a browser: clear the token but leave the cached
identity feeding route guards and you get a signed-in-looking UI in which every request fails. Two browser deltas —
the invalidation must reach the *other tabs* (§2.4), and "authoritative" excludes a timeout, 5xx, or offline window
(`resilience.md` §3.1).

### 2.4 Sign-out clears memory, caches, and in-flight work — locally, even if the server call fails

Enumerate the teardown: token, cached user, query/store caches, view data persisted to IndexedDB or web storage, open
SSE/WebSocket connections, timers and pollers. Signal the other tabs (e.g. `BroadcastChannel` or a storage event) —
server revocation ends the credential, not the pixels a second tab keeps painting from its warm cache. Teardown
proceeds even if the sign-out call fails.

## 3. The refresh race

**Applies when:** §2's shape holds *and* the server rotates refresh tokens with reuse detection (`security.md`
§2.4). Without rotation a cross-tab lock buys complexity and nothing else. This section owns the client's half of that
bargain: being a quiet client.

### 3.1 One refresh in flight per cookie jar — per tab AND across tabs

A same-tab single-flight promise (every 401 retry awaits the one in-flight refresh) is necessary and **not
sufficient**: the cookie jar is shared by every tab, so N tabs resuming after a laptop wakes present the same rotating
token N times. Add a **cross-tab lock** (e.g. the Web Locks API), the holder publishing the result where waiters read
it. Mind the scope mismatch — web locks are keyed per **origin** while a cookie jar can span subdomains via a `Domain`
cookie, so two origins sharing one refresh cookie need a coordination scope the profile names. In one audited multi-repo TypeScript workspace a per-tab-only mutex met a shared revocation lever: an ordinary
multi-tab restore tripped reuse detection and revoked the lineage, signing out sessions the user had not touched — the
honest user indistinguishable from a thief, and an alarm that fires on honest restores stops being believed.

### 3.2 The bootstrap refresh is inside the lock

The first refresh — turning a cookie into a token at app start, before any API call — is the one most likely to fire
in every tab at once, and a development double-mount (e.g. a strict-mode remount) fires it twice in one tab. It MUST
run through the same single-flight and cross-tab lock as every other refresh, never a startup path of its own.

### 3.3 A failed refresh leaves the queue parked, not the session dead

`security.md` §2.4 owns the classification. The client obligation is what happens meanwhile: keep queued requests
parked and retry per `resilience.md` §3.1 rather than tearing down. A client that treats a deploy blip as session
death signs its users out on every deploy.

### 3.4 Requests that 401 during a refresh queue, then replay exactly once

Park them, replay after the refresh resolves, and give each parked request a deadline (`resilience.md` §2) so a
stalled refresh does not hang the UI. **One replay per request, then fail** — a replay that re-401s and re-triggers a
refresh is an unbounded loop running credential traffic against your own rate limiter (`security.md` §8).

## 4. Route guards are UX, not access control

`security.md` §4 states the boundary rule. This section owns what the client build must therefore do.

### 4.1 Every privileged view's data is authorised server-side, per request

A client route guard hides a view; it does not protect data. The decidable test: for each privileged screen, **name
the server-side check that fails** when an unauthenticated or wrong-role caller requests that screen's data directly.
If the answer is "the route guard", the data is unprotected (OWASP Top 10:2025 A01 Broken Access Control).

### 4.2 A bundle served to anonymous visitors contains nothing privileged

Whatever is compiled in is published: internal pricing, prompt text, admin-only copy, unreleased feature names,
internal hostnames, seed or demo credentials. In the audited workspace exactly this happened — an admin bundle
downloadable without authentication carried proprietary prompt text and internal pricing. Privileged material MUST
arrive at runtime from an authorised endpoint, or live in a separately deployed, network-gated bundle.

### 4.3 Role-conditional UI renders from server-provided facts, not a client-side rule table

A capability table compiled into the bundle enumerates the privileged surface for anyone who reads it, and drifts from
the server's rules the first time one side changes. Ship the session's effective permissions in the session payload
and render from those; where the two disagree, the UI shows the server's answer.

### 4.4 A guard that redirects must not render first

A guard that mounts the protected subtree and redirects inside an effect flashes privileged content and fires its data
requests on the way out. Resolve auth state *before* that subtree renders; "unknown" is a third state with its own UI,
distinct from "signed out".

## 5. Output encoding and XSS sinks

*ASVS 5.0 V1 Encoding and Sanitization; OWASP Top 10:2025 A05 Injection. `security.md` §7 owns the sink-hygiene rule
(sanitiser + review comment); this section owns which sinks exist, how a sanitiser is configured, what the build owes CSP.*

### 5.1 Auto-escaping is the default, and its holes are enumerable

Framework text interpolation escapes, and that covers most output. It does **not** cover: string-to-DOM APIs
(`innerHTML`-class, `dangerouslySetInnerHTML`, `insertAdjacentHTML`, `document.write`); URL-valued attributes
accepting `javascript:`/`data:`; style and CSS-variable injection; dynamically created `script`/`iframe` elements;
`eval`-class evaluation including `Function` and string-valued timer callbacks; and server-rendered templates
interpolating into a `<script>` block or an inline handler. "We use a modern framework" is not an XSS answer.

### 5.2 A sanitiser that permits script is decoration, not a control

An HTML sink routes through a **maintained** sanitiser (e.g. DOMPurify, or the platform Sanitizer API where available)
configured with an **allowlist**: one permitting `<script>`, `javascript:` URLs, or event-handler attributes passes
review while stopping nothing, and a hand-rolled regex-stripper is that failure by default. Pin and update it like any
other security dependency — a sanitiser frozen at an old version is a known-bypass list. The accompanying review
comment is `security.md` §7's rule, mechanised here by the sink-lint guard rail: **the lint suppression is what review
reads**, so an unmarked sink is indistinguishable at audit from an examined one.

### 5.3 URL-valued input is scheme-checked before it reaches an attribute

Parse user-supplied URLs and allowlist the scheme (https, mailto, site-relative) before the string becomes an `href`,
`src`, or form action: `javascript:` in a link is XSS with no HTML injection at all. Same check for redirect targets —
an open redirect built from a `?next=` parameter is the phishing half of the same defect; validate against an
allowlist of internal paths.

### 5.4 The build is CSP-compatible; the `script-src` strategy is a profile row

Two obligations, because only one is universally achievable. **The MUST:** production builds carry no dependency on
`unsafe-eval` in `script-src` — eval-dependent tooling (template compilers, `Function`-based evaluators) is a
build-configuration problem fixable in every deployment shape, and granting the keyword returns the policy to roughly
no value against injected script. **The profile row:** how inline script is handled — per-request nonces,
hash-only, `strict-dynamic`, or a documented exemption carrying a waiver (§11.1) — because a statically hosted SPA
cannot mint a per-request nonce and the honest answer differs per surface. Trusted Types makes §5.1's sink list
runtime-enforced: cross-browser now, still defence in depth. Deploy tightened policies report-only first behind a
monitored report endpoint (`observability.md` §3.1).

## 6. CSRF — name the attack, not the header

*OWASP Top 10:2025 A01 Broken Access Control.*

### 6.1 Applicability is decided by ambient credentials

The attack: a signed-in user visits an attacker's page; that page submits a form or issues a request to your API;
**the browser attaches the session cookie automatically**; your server performs a state change as that user. The
attacker never reads the response and does not need to.

The trigger test: *is any state-changing request authorised by something the browser attaches by itself* — a cookie,
HTTP auth, a client certificate? If yes, CSRF applies. If every state change is authorised by an `Authorization`
header the app sets from memory (§2.1), it does not: no cross-site page can make the browser add that header. Record
which side each surface sits on in the profile — "we use tokens, so we're fine" holds only when no cookie is *ever
sufficient* to authorise a write.

### 6.2 Cookie-authorised state changes carry an anti-CSRF token and never ride a safe method

Where cookies authorise writes, every unsafe request carries a synchroniser token (per session, verified server-side
before the handler runs) or a signed double-submit cookie. And **no state change on GET or HEAD** — a mutating GET is
reachable from an `<img>` tag, defeating every token scheme because no token was ever expected there. The refresh
endpoint needs this specifically: it is cookie-authorised by construction (§2.1) and mints credentials, even in an
otherwise pure-bearer app.

### 6.3 `SameSite` is a layer, not the control

`SameSite=Lax`/`Strict` (the attribute itself is `security.md` §7) removes the easiest form of the attack and is not
the whole defence: `Lax` still permits top-level GET navigations, browser defaults vary, and a compromised same-site
subdomain is unaffected. It reduces blast radius; §6.2 is the control. Cite `draft-ietf-httpbis-rfc6265bis` for `SameSite` — RFC 6265 does not
define it.

## 7. Third-party code in a privileged origin

*OWASP Top 10:2025 A03 Software Supply Chain Failures. `security.md` §10 owns the package case; this section
owns non-package code — the tags you add by hand.*

### 7.1 Admission is the control — decide it like a permission grant

Every `<script>` tag, tag-manager container, analytics or session-replay snippet and chat widget executes with the
**full authority of the origin**: the DOM, the in-memory token (§2.1), and every character the user types. Adding one
to a privileged surface — one rendering admin function, billing, or personal data — is a decision recorded where the
workspace already records decisions (the register named in `supply-chain-and-build-integrity.md` §6.1, not a new
approval system) and inventoried in this file's profile table. Capture-based tools additionally exfiltrate what they
record: mask or exclude sensitive fields by default (`security.md` §12).

### 7.2 Externally hosted scripts carry Subresource Integrity, or they are not external

Any script from a host you do not control MUST carry an `integrity` hash and `crossorigin`, so a swapped or
compromised artifact **fails to execute** rather than executing as you. Where the vendor ships a deliberately mutable,
self-updating URL (most tag managers) SRI is impossible by construction — take that decision explicitly: self-host a
pinned copy, or record that the vendor can execute arbitrary code in your origin at any time. A `connect-src`
restricted to known hosts (§5.4) bounds where a compromised script can send what it takes.

## 8. Accessibility

*WCAG 2.2 and WAI-ARIA 1.2. This file is the library's only accessibility lane and covers the rendered UI of any
client. The conformance level and any regulatory obligation are profile rows (§8.6); the rules below are testable code
obligations that hold regardless.*

### 8.1 Every interactive element is keyboard reachable and operable

Reachable in DOM order via Tab, operable by Enter/Space (and arrow keys for composite widgets), with no trap: WCAG 2.2
SC 2.1.1 Keyboard (A) and SC 2.1.2 No Keyboard Trap (A). Never use positive `tabindex` values — they reorder the tab
sequence document-wide, so the damage surfaces in a component that never changed. A modal that traps focus on open but
not on close is the recurring instance.

### 8.2 An interactive element built from a non-interactive tag needs explicit semantics

A `div` or `span` with a click handler is invisible to assistive technology and unreachable by keyboard. Either use
the native element (`button`, `a[href]`, `input`, `select`, `details`) — which supplies role, focusability, keyboard
behaviour and state for free — or supply all of it explicitly: `role`, an accessible name, `tabindex="0"`, key
handlers, and the state attributes the role requires (`aria-expanded`, `aria-checked`, `aria-selected`). WCAG SC 4.1.2
Name, Role, Value (A); role semantics per WAI-ARIA 1.2. **Native first is the rule; ARIA is what you owe when you
decline it.** Recognisable failure: a click-handled `div` styled as a button — invisible in every screenshot.

### 8.3 Focus is visible, and stays visible

Never remove a focus indicator without replacing it — SC 2.4.7 Focus Visible (AA) — and the replacement must survive
layout: SC 2.4.11 Focus Not Obscured (Minimum) (AA, new in 2.2); sticky headers, cookie banners and floating toolbars
are the recurring causes. Focus is also *managed*: opening a dialog moves focus into it, closing returns it to the
invoker, a route change moves it to the new view's heading.

### 8.4 Contrast and target size are properties of the design tokens

Text meets 4.5:1 (3:1 for large text) — SC 1.4.3 Contrast (Minimum) (AA); UI component boundaries and meaningful
graphics meet 3:1 — SC 1.4.11 Non-text Contrast (AA); pointer targets are at least 24×24 CSS pixels or adequately
spaced — SC 2.5.8 Target Size (Minimum) (AA, new in 2.2). Check these in the token set rather than per component, and
once **per theme**: a palette that passes in light mode frequently fails in dark.

### 8.5 Motion is preference-aware, and authentication does not require a memory

Respect `prefers-reduced-motion` for any non-essential animation, parallax, or auto-playing transition: one media
query, and the vestibular harm it prevents is real (SC 2.3.3 Animation from Interactions is AAA; the preference is
cheap to respect at any target). Authentication flows MUST NOT require a cognitive function test — SC 3.3.8 Accessible
Authentication (Minimum) (AA, new in 2.2). The concrete client-side instance: blocking paste into a password or
one-time-code field, a one-line handler that breaks every password manager. Delete it.

### 8.6 The conformance target and any regulatory obligation are declared, not assumed

The profile records the target (e.g. WCAG 2.2 Level AA), the surfaces it covers, and the audit cadence. Whether an
accessibility *regulation* binds a given product depends on jurisdiction, sector, size, and customer base — so the
profile records the determination and its reasoning, naming the regime where one applies (e.g. EN 301 549 in an EU
context). **A recorded "no, because…" is a complete answer; an unrecorded answer is the finding.** This master states
no verdict about any organisation's obligations.

## 9. Client observability

`observability.md` §7.3 owns reporting mechanics, §6.1 log hygiene (which client reports obey unchanged), and §3 alarm
classes. This section owns the web-specific obligation.

### 9.1 An error that dies in the user's console is not observed

Browser errors reach no aggregator by default: a component crash, an unhandled promise rejection, a failed chunk load,
or a CSP violation is visible only to the user who hit it, and users report almost none of it. Every web client MUST
capture them — an error boundary per route subtree plus global `error`, `unhandledrejection`, and
`securitypolicyviolation` handlers — and forward them off the device. **Sampling is fine; zero is not.** The sink, and
whether reports carry the API-side correlation id (`observability.md` §5.1), are profile rows; the build identifier
(§10.2) is not — without it a spike maps to no deploy.

## 10. Build/runtime coupling for bundles

`config-and-environment.md` §5 owns which values may reach a client bundle and §8 build/runtime coupling generally;
only the web-specific consequences belong here.

### 10.1 An inlined value is frozen on CDN edges and in user caches

The browser-specific half of `config-and-environment.md` §5: a build-time substitution is not merely hard to change,
it is **unrecallable** — copies already sit on CDN edges and in users' HTTP caches, and the old bundle keeps serving
the old value for as long as those live. That is the cost to weigh when §5's decision is made; the profile's bundle
table carries the per-value answer, and anything that must change without a release is fetched at runtime.

### 10.2 The bundle names its build, and the app can tell it is stale

Every build embeds an identifier (commit or build id), reported with client errors (§9.1) and readable in support
flows — unconditional, and the base of everything below. Dynamic-import failures are the common symptom of a
superseded bundle: allow **one** reload attempt, with a marker preventing a loop, and **count them** — a rising rate
means the deploy is stranding sessions. *Applies when the API can advertise the current client build id* (a header on
any response suffices): the long-lived tab compares and prompts a reload rather than failing unreproducibly. Where it
cannot, the profile records that (compare `mobile-app.md` §4).

## 11. Accepted gaps

### 11.1 A rule you cannot yet satisfy is a dated waiver, not a silence

Several rules here are gated on facts a project may not have: a browser test harness (§3.1's guard rail), ownership of
the served headers (§5.4), an error aggregator (§9.1), a build id the API can advertise (§10.2). Each gap MUST appear
as a **dated waiver with an expiry** in the register the workspace already keeps —
`supply-chain-and-build-integrity.md` §6.1 owns that mechanism and this file adds no second one. Two rules are
deliberately **non-waivable**, because their failure is immediate and total rather than degraded: §2.1's
no-developer-convenience-exception and §6.2's no-state-change-on-GET. An unrecorded gap is worse than an expired one —
nothing surfaces it.

## Failure shapes

Named patterns, genericised. Recognise one, cite it by name.

- **The refresh stampede** — a laptop wakes, six tabs resume, six refreshes present the same rotating token; a
  per-tab-only mutex makes the honest restore indistinguishable from theft, and the reuse alarm both logs the user out
  and stops being believed. (§3.1)
- **The guard that ships the secret** — a route guard hides an admin view while the bundle serving it, downloadable by
  anyone, carries the pricing and prompt text that view would have rendered. (§4.2)
- **The escaped-by-default illusion** — a framework that escapes text everywhere, one `innerHTML`-class call for "just
  this rich-text field", and stored XSS running in every admin's session with their token in reach. (§5.1)
- **The vendor tag with no hash** — a self-updating third-party script on a privileged page: the vendor's pipeline is
  inside your origin, and no lockfile, scanner, or review sees what ships. (§7.2)

## Checklist

Before merging a web-client change. Boxes 1–7 are answerable **from the diff plus the profile**; the last two need a
rendered result or a fact from another repo, and say so.

- [ ] Token handling touched: nothing written to `localStorage`/`sessionStorage`, no dev escape hatch?
- [ ] Refresh path touched: single-flight **and** cross-tab lock still cover it, bootstrap included; a blip still leaves the queue parked rather than ending the session?
- [ ] Diff adds a constant, string, or config to a bundle: safe for an anonymous reader to hold, and changeable without a redeploy if it ever must change?
- [ ] New HTML sink: allowlist sanitiser, with the lint suppression carrying the reason? New URL-valued attribute or redirect target: scheme/path allowlisted?
- [ ] New third-party script on a privileged surface: decision recorded in the register and profile table; external URL carries `integrity` or is vendored?
- [ ] New interactive element: native tag — or role + accessible name + `tabindex` + key handlers + state attributes? Focus moved on dialog open/close and on route change; no positive `tabindex`; no paste-blocking on a password or OTP field?
- [ ] New failure path: captured by a boundary or global handler and forwarded with the build id, not only `console.error`? Chunk-load failure handled with a single bounded reload?
- [ ] *(rendered result)* Focus indicator visible and unobscured, target ≥24×24, contrast checked **in every theme** — not inferable from a token diff.
- [ ] *(other repo / judgement)* New privileged view: the server-side check authorising its data is named, and it is not the route guard (§4.1)? New state-changing call: cookie- or header-authorised per the profile's credential row (§6.1)?

## Guard rails

CI checks that make this standard enforceable, not aspirational. Where a rule is judgement-only it says so; where a
gate needs tooling a project lacks, that gate's absence is a waiver (§11.1), not a deletion.

- **[web-client.GR1]** **Web-storage and sink lint** — a rule or CI grep banning `localStorage`/`sessionStorage` writes outside an
allowlisted module (§2.1), plus rules for the string-to-DOM and `eval`-class sinks (e.g. `react/no-danger`, `no-eval`,
an `innerHTML` grep) failing unless suppressed with a comment; the suppression is what review reads (§5.2,
`comment-standard.md`).
- **[web-client.GR2]** **CSP build gate** — build and smoke-test under the production policy, failing on any violation. *Where the team
owns the served headers*, add an integration test asserting the header set; where a CDN or platform serves them, the
profile names who does and the assertion runs against the deployed response.
- **[web-client.GR3]** **Multi-tab refresh test** — *where §3 applies and a browser-automation harness exists*: N contexts against one
cookie jar, asserting exactly one refresh reaches the server and no lineage revocation fires. The only check that
catches §3.1 before users do.
- **[web-client.GR4]** **Built-artifact scan** — CI greps the built bundles (§4.2) for credential patterns, internal hostnames, and the
profile's privileged strings, reusing the secret-sweep patterns in `security.md`'s guard rails; it also fails any
`<script src>` to an external host without `integrity`, and diffs the third-party set against the profile table (§7).
An unfilled string list still runs the generic patterns and reports itself empty rather than passing silently.
- **[web-client.GR5]** **Automated accessibility scan** (e.g. an axe-core integration) in component and end-to-end suites, scoped to the
profile's conformance target, new violations failing the build. **Tooling detects only a subset of WCAG failures — the
rest of §8 is judgement**, verified by a keyboard-only and a screen-reader pass at the profile's cadence: treating the
scanner as the control is the mistake.
- **[web-client.GR6]** **Client-error, CSP-report and chunk-failure alarms** (`observability.md` §3) — a deploy that raises any of those
rates is caught by an alarm, not by support tickets.
- **[web-client.GR7]** **§4.1 and §6.1 are judgement-only.** No tool can tell you a route guard stands in for a server check, or that a
cookie is *sufficient* to authorise a write; both are review questions answered in the profile.
