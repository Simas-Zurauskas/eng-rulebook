## 0. Scope — when this standard applies

This applies to any project with the **wiki-system setup**:

- A **workspace** directory holding, as siblings: one or more **code repos**, a generated
  docs root `wiki-{project}/` (referred to below as `<WIKI>/`), and a `CLAUDE.md`.
- Documentation generated from source by `wiki-system` into `<WIKI>/`, with the **AI track**
  (`<WIKI>/AI/**`) always present — invariants, contracts, runbooks, flow maps, per-repo
  reference — and refreshed on demand via `/wiki-system recheck`.

If your docs are generated from your code, this standard tells you what is left for comments
to do. **That is a much smaller job than most codebases assume.**

**External anchors** — name + version + status, never URLs. *Anchors verified 2026-09-06;
re-verify anything older than 12 months (`_authoring.md` rule 6).*

## 1. Core principle — the layering every rule below follows from

Three artifacts describe the system. They have very different properties:

| Artifact | Ground truth? | Verified against what? | Regenerated by what? |
| --- | --- | --- | --- |
| **Code** | **Yes** — it executes | Tests, typecheck, CI | — |
| **Wiki** (`<WIKI>/**`) | No — derived | **The source code**, by wiki-system verifiers | `/wiki-system recheck` |
| **Comments** | No — derived | **Nothing** | **Nothing** |

wiki-system's contract is explicit: *the verification ground truth is always the source code.*
The wiki is re-derived and re-verified on demand. Code is enforced by the compiler and tests.

**Comments are the only artifact in the system with no verification mechanism and no
regeneration path.** Nothing fails when a comment goes wrong — no test reddens, no build
breaks, no verifier complains. That asymmetry is the entire basis of this standard:

> Because comments cannot be checked, they must carry **only what the other two layers
> cannot** — and nothing else.

### 1.1 Why duplication is actively harmful, not merely wasteful

A comment restating what the wiki already documents costs you three times:

1. **It misleads at the point of edit** the moment it drifts — and it will, because nothing
   catches it.
2. **It taxes every regeneration.** Each `recheck` re-adjudicates the code/comment conflict
   (an audit pass is on the order of ~50 verifier dispatches).
3. **It earns a permanent wiki passage refuting it — and that passage rots too.** The wiki
   starts documenting your code's lies instead of your code.

That third step is the trap. Once the wiki says *"the comment at X is wrong, trust the code"*,
you are maintaining a **refutation layer**: a second thing to keep in sync, which fails
silently in the *opposite* direction. When the comment gets fixed, the refutation is now the
lie — and it teaches agents to distrust a comment that has become trustworthy.

**Rule: never build a refutation layer. Fix the comment.**
A wiki passage adjudicating a comment is a bug report, not documentation. Close it in the code.

## 2. The test

Before writing or keeping any comment, ask:

> **Would someone who has already read the wiki still get this wrong while editing *this line*?**

- **No** → the wiki owns it. Delete it. Don't write it.
- **Yes** → it earns its place. One or two sentences.

Then the follow-up:

> **Could a test enforce this instead?**

- **Yes** → **write the test.** A "keep these in sync" comment is a test you didn't write.

**Proximity is the whole value proposition.** If you'd want the information *before starting
the task*, it belongs in the wiki. If you need it *at the instant your cursor is on that line*,
it belongs in the code. Comments are not for explaining the system; they are for stopping a
specific edit from going wrong.

## 3. What MUST stay (never cull these)

Four categories. Everything else is a candidate for deletion.

### 3.1 Machine-consumed text — this is spec, not commentary

Some comment-shaped text is an input to a build step. It reads like prose and gets deleted by
prose culls. It is not prose.

- **Doc comments that generate an API spec** (e.g. OpenAPI — formerly Swagger — JSDoc scanned
  by a generator, and consumed downstream by client type-codegen). This *is* your API contract.
  - **Know the generator's glob.** A block outside it is **silently ignored** — it never
    errors, it just never reaches consumers. Record the glob in Appendix A.
  - **Know where it ships.** If clients codegen from it, that text reaches other repos and
    other teams.
- **String literals that feed the spec** (schema `description:` fields). Documentation-shaped, build input.
- **Directive reasons** — a suppression comment is machine-consumed text, and the reason beside it
  is the only record of why the rule is off. **Always include one**; a bare directive is a defect.
  Two obligations ride on every directive: **name what is suppressed** (a rule id or error code —
  without it it silences future, unrelated failures on that line forever), and **say why**.

  | Stack | Directive | Naming the target, and where the reason goes |
  | --- | --- | --- |
  | TypeScript | `eslint-disable*`, `@ts-expect-error`, `@ts-ignore` | the rule name on `eslint-disable`; ESLint reads a description only after a ` -- ` separator (v7.0.0+), and without it the words parse as rule names and the reason is silently lost |
  | Python | `# noqa`, `# type: ignore`, `# pragma: no cover` | `# noqa: E501`, `# type: ignore[arg-type]` — **bare forms suppress the whole line**; reason follows the code |
  | PHP | `@phpstan-ignore`, `@psalm-suppress`, `@var` | the error identifier; reason on the preceding line |

  **Prefer the expecting form where the tool has one** (`@ts-expect-error`, or an analyser's
  unused-suppression reporting): it fails when the suppressed problem *stops* occurring, so a
  directive cannot outlive its cause. A plain ignore never expires.

> **Litmus:** if deleting the text changes a build output or a shipped artifact, it is spec.
> It is not subject to §4.

### 3.2 Constraints invisible in the code

Facts the compiler cannot express and a competent reader cannot infer. This is the core of a
healthy comment budget:

- **Third-party behaviour you learned the hard way** — an undocumented quirk, a vendor API
  that ignores a parameter, a service that returns 200 on failure. Unknowable from code;
  violating it fails silently.
- **Ordering and coupling between things that don't reference each other** — "this array's
  order is load-bearing because the string at *that* site names the elements positionally";
  "upload before transform so the paid-for artifact survives a crash in the next step".
- **Platform traps that pass CI and fail at runtime** — e.g. a deliberately lazy import
  because the module isn't linked on one platform, so a top-level import typechecks, lints,
  and then crashes on load. The comment is the only guard.
- **Race conditions and sequencing** — "notify *before* the async delete"; "this lock exists
  because two tabs restoring at once look like credential theft to the server".
- **Incident memory** — why an error is rethrown rather than swallowed, because swallowing it
  once caused a silent production downgrade. One sentence; name the incident's shape.

### 3.3 Cross-repo couplings nothing enforces

In a multi-repo workspace the repos typically share no build. Every value that must agree
across a seam is hand-copied. The failure is **silent**: both sides compile, both suites pass,
production quietly degrades.

Such a comment is load-bearing — and it **must name the failure mode**, not just assert the
mirror. "Mirror of X" is useless; "if these disagree, every Y silently degrades to Z with no
error surfaced" is actionable.

**Prefer a test to a promise.** The strongest form pairs the comment with a pin:

```
// Hand-mirrored with <other-repo>/<path> — the repos can't import each other.
// Pinned by a unit test on BOTH sides. A rename here that the other side no
// longer matches degrades <X> to <fallback> silently, with no error.
```

That comment earns its confidence *because the test exists*. When you **cannot** pin it, say so
explicitly and name what hides the drift:

```
// <other-repo>/<path> is the source of truth — edit both together.
// Unpinned: no test enforces this, and because <runtime override> masks it,
// drift stays invisible until <condition>, when this stale copy silently ships.
```

**Never let a comment imply a guarantee that nothing provides.**

### 3.4 "This looks like a bug but is deliberate" markers

The highest-signal comments in any codebase, and the highest-signal by far in a partially-built
one. They stop the next reader — human or agent — from "fixing" working code:

- Deliberate non-persistence, deliberate duplication, a deliberate fail-open.
- A deliberate seam or placeholder in a half-built flow: an agent editing that file needs to
  know the dead-end is intentional **at the point of edit**. The wiki cannot substitute — by
  the time you're editing the line, you're past the point of reading a reference page.
- A constraint imposed from outside the code (a contract, a spec, a legal or scope decision):
  "read-only by design per <decision>" prevents someone helpfully adding the write path.

Phrase these as an instruction, not an observation: *"do not 'fix' this by adding X"* beats
*"X is not persisted"*.

## 4. What comments must NOT contain

### 4.1 Architecture and subsystem narrative — the wiki owns this

No multi-paragraph file headers explaining how a subsystem fits together. No cross-repo flow
tours. No usage manuals with examples. No ASCII state tables. That is precisely what the
generated AI track holds — and unlike your header, **it gets re-verified against the code**.

Replace a narrative header with a **one-line purpose statement**. Then look again: constraints
(§3.2) are frequently buried inside narrative prose. **Keep the constraint kernel; drop the
tour.** A blind prose sweep that deletes whole headers will take load-bearing facts with it —
this is the single most common way a comment cleanup causes an outage.

### 4.2 Restatement

If the code says it, don't. `// increment the counter` above `count++`. `// clear the timer on
unmount` above a cleanup effect. This is the least harmful bucket and rarely worth a dedicated
pass — but never add to it.

### 4.3 Anything false

A wrong comment is worse than no comment: it is trusted, and it is not checked.

> **When you change a line, the comment above it is part of your diff.**

The recurring shapes — the contradicted default, the inverted model, the obituary for a living
thing, the wrong contract — are named with their remedies in **Failure shapes** below.

### 4.4 Pointers to non-wiki markdown

**The most common rot in this setup, by a wide margin.** Planning docs, design docs, RFCs and
scratch notes get renamed, merged into the wiki, and deleted. The comments citing them do not.
Nothing catches it — a dead `.md` reference fails no build.

Legal targets are in §5. Planning docs are never one of them. (Expect to find these in your
docs' own hand-written notes too, not just in source.)

### 4.5 Citations of `CLAUDE.md`

`CLAUDE.md` is itself generated/refreshed from the code and summarises it. A comment citing it
as authority creates a **circular chain**: code comment → CLAUDE.md → code comment, with no
ground truth anywhere in the loop. In practice both ends drift and each cites the other as
proof. Point at the wiki, or at code.

## 5. Rules for references

### 5.1 Only two legal targets

a path under `<WIKI>/**`, or a source file path.

### 5.2 Never a planning doc, an RFC, a README, or any `.md` outside the wiki

**Never** a planning doc, an RFC, a README, `CLAUDE.md`, or any `.md` outside the wiki.

### 5.3 Never inside machine-consumed text (§3.1)

An API description ships to consumers;
internal doc paths do not belong in it. Make such descriptions self-contained.

### 5.4 One canonical pointer per concept

The module that *owns* a concept carries the wiki
link; every other site points at **that module**. Don't scatter the same long wiki path
across a dozen files — that creates a dozen things to rot, and the path is exactly the kind
of thing a wiki restructure invalidates.

### 5.5 External citations are fine when labelled as external

Citing a framework's own docs
is legitimate and stable in a way your deleted design doc is not. Label it so automated
link checks can whitelist it.

### 5.6 Prefer stable anchors

Prefer **stable anchors**: a file path or exported symbol name over a line number. Line
numbers are wrong within a week.

## 6. Style

- Say **why**, not **what**. Assume the reader can read code but cannot read your mind.
- One or two sentences. If it needs a paragraph, it's wiki content — or it's hiding a
  constraint that should be extracted to one line.
- **Prefer positive, present-tense statements of the current design.** Avoid archaeology
  ("no longer", "anymore", "used to", "was renamed from") — it dates instantly and describes a
  system the reader cannot see. State what *is*.
- **Know whether your formatter reflows comment text, and let that decide who wraps.** Most leave
  comment prose as written, so the author wraps to the project's width; some reflow by default,
  and there hand-wrapping is undone on the next format run — a churning diff nobody authored.
  Check the formatter you actually run: this is a per-toolchain fact, not a universal one.
- **No `TODO`/`FIXME`/`XXX`/`HACK` markers.** They are unowned, undated, and unactionable, and
  they decay into noise that trains readers to skip comments. Either fix it, or write a real
  §3.4 comment explaining the deliberate gap.
- **No commented-out code.** That's what git is for.

## 7. Workflow rules

- **Never hand-edit the generated wiki** (`<WIKI>/**`, excluding hand-written areas such as
  `notes/`) as a side effect of feature work. It is generated; out-of-band edits conflict with
  regeneration and are silently overwritten. Fix the **code and its comments** — the ground
  truth — then run `/wiki-system recheck` and let the wiki re-derive.
- **Order matters when cleaning up.** Fix comments **first**, then `recheck`, then trim any
  wiki-owned narrative (§4.1). The wiki lags the code between rechecks — it is derived, not
  live. Trimming a comment against a stale wiki page deletes accurate prose in favour of a
  stale reference, and you will not notice.
- **After changing machine-consumed text, re-run the downstream codegen — in every consumer,
  never just one.** Generated client artifacts are build output that can silently carry a lie
  long after the source of truth was corrected. A stale generated file is a shipped defect.

## Failure shapes

Named patterns from real audits, genericised. Recognise one, cite it by name.

- **The contradicted default** — a comment naming one default directly above a different one.
  The cheapest rot to find and the most common. (§4.3)
- **The inverted model** — a security or access claim that was true before a migration ("the
  bucket is public"), whose *entire stated rationale* is now obsolete. These need the reasoning
  **re-derived**, not a word swapped: if the premise is gone, ask whether the code it justifies
  still has a reason to exist. (§4.3)
- **The obituary for a living thing** — "X was dropped/replaced", where X is still there. (§4.3)
- **The wrong contract** — a component documenting a consumer relationship its consumer doesn't
  honour (e.g. "the exit code is the contract" when the caller branches on something else
  entirely). Verify against the **consumer**, not intuition. (§4.3)
- **The dead pointer** — the most common rot in this setup by a wide margin: a comment citing a
  planning doc, design doc, RFC or scratch note that was since renamed, merged into the wiki, or
  deleted. Nothing catches it — a dead `.md` reference fails no build. (§4.4)
- **The circular chain** — a comment citing `CLAUDE.md` as authority, which is itself derived
  from the code: code comment → CLAUDE.md → code comment, with no ground truth in the loop.
  Both ends drift and each cites the other as proof. (§4.5)
- **The stale-wiki trim** — trimming a comment against a wiki page that has not been re-derived
  since the code changed, deleting accurate prose in favour of a stale reference. The wiki lags
  the code between rechecks; fix comments first, *then* recheck, *then* trim. (§7)

## 8. Checklist

Before committing a comment:

- [ ] Would a wiki reader still get this wrong **at this line**? (No → delete it.)
- [ ] Could a **test** enforce it instead? (Yes → write the test.)
- [ ] Is every claim **true of the code as it now stands** — verified, not assumed?
- [ ] Does it reference only `<WIKI>/**` or a source path?
- [ ] Free of `CLAUDE.md` citations and dead planning docs?
- [ ] If it's machine-consumed: no internal refs, and downstream codegen re-run everywhere?
- [ ] If it asserts a cross-repo mirror: is it pinned by a test — or does it say it **isn't**,
      and name the silent failure?
- [ ] **Did you change the line above it without changing it?**

## 9. Adopting this in a new project

### 9.1 Don't fork this file out of the library

It ships inside the `eng-rulebook` skill; a
workspace adopts it by copying the whole skill folder (`references/README.md` owns the
adoption model). Scattering per-project copies recreates exactly the drift problem it
exists to prevent.

### 9.2 Create the project's profile

from the Appendix A template, and keep it *with the
project* (e.g. `<home>/profiles/comment-profile.md`). It records the project's
machine-consumed globs, unpinned mirrors, and deliberate seams. Without it, agents cannot
tell §3.1 spec from §4.1 prose — and will delete a contract. Link it from `CLAUDE.md` too.

### 9.3 Baseline before changing anything

measure the buckets (§3 keep / §4.1 narrative /
§4.2 restatement / §4.3 stale). **The usual finding is that volume is fine and truth is
the defect** — in one audited four-repo project, ~70% of comments earned their keep, ~18%
was wiki-owned narrative, ~5% restatement, and **~0.6% was stale**. That 0.6% caused every
real problem, including a latent bug, ~30 dead doc pointers, a false cross-repo contract,
and a fiction that had propagated into two clients' generated types. **Don't run a comment
purge; run a truth pass.**

### 9.4 Then, in order

fix truth → `recheck` → trim narrative → add guard rails (§10).

## 10. Guard rails worth building

Cheap CI checks that make this standard enforceable rather than aspirational:

- **[comment-standard.GR1]** **Reject `.md` references in source that don't resolve on disk.** Catches §4.4 entirely.
  Whitelist labelled external citations (§5.5).
- **[comment-standard.GR2]** **Reject machine-consumed blocks outside the generator's glob** (§3.1). Prevents the
  silent-ignore trap.
- **[comment-standard.GR3]** **Pin every cross-repo mirror with a test on both sides** (§3.3). Each un-pinned mirror is a
  silent production failure waiting for a rename.
- **[comment-standard.GR4]** **Fail CI on a stale generated artifact** — re-run codegen and diff. Catches §7's shipped lie.
- **[comment-standard.GR5]** **Reject bare suppression directives without a target and a reason** (§3.1).
  Per stack: `eslint-disable`/`ts-expect-error` (TypeScript); ruff `PGH003` and `PGH004`, which reject
  bare `# type: ignore` and bare `# noqa` (Python); the analyser's blanket-suppression and
  unused-suppression reporting (PHP). Same obligation, three spellings — and in Python and PHP the
  bare form is the common one, because the tools accept it silently.
