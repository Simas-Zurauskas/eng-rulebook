# Software Supply Chain & Build Integrity Standard

> **Type:** Generic, reusable standard · **Rev:** 2 (2026-07-28)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
> Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs everything between "someone else's code exists" and "our artifact is deployed": which
> third-party releases are admissible into the tree, the integrity of the pipeline that builds them,
> the identity it authenticates with, and the provenance the artifact carries. Core idea: **the build
> system is the highest-privilege system in the workspace, so it is governed like production.**

## 0. Scope

**Applies whenever a repo resolves third-party code or runs a pipeline that holds a credential.**
Assumed context: a multi-repo TypeScript workspace — backend API, web client(s), mobile app,
worker(s) — with docs generated by wiki-system and types code-generated from the running API's spec.
Rules are stack-agnostic; managers, CI platforms and tools appear only as labelled examples.

**Owns:** dependency admission (cooldown, provenance-before-lockfile, namespace reservation,
install-script policy), CI step and image pinning, workflow token scope and untrusted-input handling,
build-time identity, SBOM generation, signed provenance and its verification, supply-chain waivers,
compromise response.

**Does not own** (one-line cross-refs only):

- The vulnerability scanner and its severity gate → `security.md` §10. Here: which releases are
  admissible at all, and the integrity of the pipeline that runs that scanner.
- *That* a lockfile exists and installs are frozen (`tooling-and-workspace.md` §2.2), and *which* build
  image is chosen (`tooling-and-workspace.md` §7.3). Here: what may be **written into** that lockfile,
  and that whichever image is chosen is digest-referenced — reproducing a compromised tree faithfully is
  that standard succeeding and this one failing.
- Runtime values the server reads → `config-and-environment.md`; here, the credential the *runner*
  holds, not the one the process loads.
- The **regulatory-applicability register** → `data-protection.md` Appendix A. One register, not two.
  Here: what an obligation means for a build once that register says it applies (§6.4).

**External anchors** — name + version + status, never URLs. *Checked against primary sources on
2026-07-28: vendor settings docs, release APIs, the Official Journal text; re-verify anything older than
12 months (`_authoring.md` rule 6).*

not a registry of record; Yarn's duration-suffix form has reported parsing bugs, so §2.1 uses numbers.

## 1. Core principle

The build system is the only system in the workspace holding all three of these at once: **credentials
for every environment it deploys to and every registry it publishes to**; **third-party code executing
by default on every commit** (install scripts, CI actions, base images, formatters, test runners); and
**the output everyone downstream trusts without inspecting it.** Application code has at most one. That
concentration is why one compromised transitive dependency in a build step is a full-workspace
credential compromise, and why supply-chain findings sit high on consequence by construction.

- **Reproducibility is not integrity.** A frozen lockfile guarantees everyone builds the *same* tree.
  It says nothing about whether that tree should exist. (`tooling-and-workspace.md` §2.2.)
- **Trust is admission plus identity.** What may enter the tree (§2), and who the pipeline proves it
  is when it spends its privileges (§4). Every other rule serves one of the two.

## 2. Admission — what may enter the tree

*OWASP CI/CD CICD-SEC-3 Dependency Chain Abuse.*

### 2.1 A minimum release age is enforced by the package manager, not by policy

Every repo MUST configure a **cooldown**: a newly published version is not resolvable until it has
existed for a declared minimum. Registries take compromised versions down quickly — pnpm's supply-chain
guidance states that "the npm registry usually removes the affected versions within hours" — so even a
short cooldown removes most of the exposure window with no detection capability of your own. **The
profile declares the value** (24 hours is a common floor; some run 3–7 days), so a shorter declared
value is a decision to read, not a finding. A wiki page is not a control; the resolver MUST refuse.

**The unit differs per manager, and a value against the wrong key is off by orders of magnitude** — `7`
is one week in npm, seven minutes in pnpm and Yarn, seven seconds in Bun. Key spelling, casing and file
location also move between manager **majors**, so read the manager's own settings page for the version
you pin. Managers in the assumed stack, as examples — the rule is the cooldown, not these:

| Manager (minimum version) | Key | Unit | File |
| --- | --- | --- | --- |
| npm (≥ 11.10) | `min-release-age` | **days** | `.npmrc` |
| pnpm (≥ 10.16; default 1440 from 11.0) | `minimumReleaseAge` | **minutes** | `pnpm-workspace.yaml` |
| Yarn Berry (≥ 4.10) | `npmMinimalAgeGate` | **minutes** (bare number) | `.yarnrc.yml` |
| Bun (≥ 1.3) | `minimumReleaseAge` (under `[install]`) | **seconds** | `bunfig.toml` |

- The value MUST live in a **committed, repo-scoped** file; a user-level setting protects the one laptop
  that ran the command and no CI runner. Only a manager new enough to know the key honours it — an
  unrecognised key is ignored in silence, which reads identically to enforcement — so pin the manager
  version (`tooling-and-workspace.md` §2.1) as part of this control.
- The cooldown delays security patches, so declare a **break-glass** in the profile: an exclusion list
  where the manager offers one (e.g. pnpm's `minimumReleaseAgeExclude`), otherwise a time-boxed override
  in one named commit — "we lowered it during an incident and never raised it back" is the failure that
  row prevents. Update bots resolve versions themselves and MUST carry their own cooldown config; the
  manager's setting does not reach them.

### 2.2 A dependency's existence and provenance are verified before it enters a lockfile

Adding a package name MUST be preceded by confirming, from the registry, that the package exists under
that exact name, its repository link resolves to real source, and its publishing history is not one
release old with a name close to a popular package. This is the **hallucinated-package** surface:
Spracklen et al. (USENIX Security 2025) measured hallucination rates of **at least 5.2% for commercial
models and 21.7% for open-source models** and **205,474 unique hallucinated package names**, many
recurring across repeated identical prompts. A name an assistant reliably suggests and that does not
exist is a **registerable** name, and registering it is cheap.

- An AI-suggested dependency is **unverified until resolved against the registry**. Agents: never write
  an import for a package you have not confirmed exists. Typosquat distance is evidence — a
  one-character or hyphenation variant of a popular package is refused, not investigated later.
- New direct dependencies enter in their **own commit**, so the lockfile diff is reviewable: a feature
  commit adding 400 lockfile lines is not reviewed by anyone.

### 2.3 Internal namespaces are reserved and resolution is pinned to the intended registry

**Applies when:** the workspace publishes internal packages or consumes any private registry. A workspace
with no private packages records that in the profile and the rule is satisfied.

Internal packages MUST live under a **reserved namespace/scope** whose name an attacker cannot claim, by
**either** of two co-equal paths recorded per scope in the profile: **(a)** the scope is mapped in
committed config to exactly one registry with public fallback disabled, **or (b)** the public equivalent
of every internal name is held defensively. Neither is more correct — some registries restrict
placeholder publication, some resolvers ignore scope mappings on a private miss. With neither, a
resolver preferring the highest version installs an attacker's package at version `99.0.0` — the
dependency-confusion class (Birsan, 2021).

### 2.4 Install-time script execution is allowlisted, not ambient

Package install scripts execute arbitrary third-party code on the installing machine with that machine's
credentials — the mechanism by which a self-replicating npm worm (September and November 2025 waves;
CISA alert 2025-09-23) harvested developer and CI credentials and republished itself from the maintainer
accounts it stole. CI installs MUST therefore disable dependency lifecycle scripts by default and
allowlist the few packages that genuinely need them (e.g. npm `ignore-scripts`; Yarn Berry
`enableScripts: false` plus per-package `dependenciesMeta.<pkg>.built`; pnpm's default block plus its
build-allowlist setting). The allowlist is committed and reviewed like code, and each entry names **why**
that package must build. "It broke without it" is a diagnosis, not a justification.

### 2.5 Tools a workflow fetches at runtime are pinned like steps

An admission control applied only to the manifest is bypassed by one line of CI config. Every package or
tool a workflow fetches at runtime — a global install, a `curl | sh` bootstrap, an extra binary pulled
before the build — is a dependency of the build, and MUST be **pinned by digest and recorded on the
allowlist (§3.1)**; where a package manager mediates the fetch, §2.1–§2.4 apply too. No resolver
mediates a piped shell script, so pinning is the only control reaching it.

## 3. Pipeline integrity — the runner is a production host

*OWASP CI/CD CICD-SEC-1 Insufficient Flow Control, CICD-SEC-4 Poisoned Pipeline Execution,
CICD-SEC-5 Insufficient PBAC.*

### 3.1 Every CI step is pinned by trust class, from an allowlist

Version tags are **mutable**. In CVE-2025-30066, an attacker re-pointed the existing tags of a widely
used CI action (v1 through v45.0.7) at a malicious commit that dumped runner secrets into build logs —
an action referenced by over 23,000 repositories, of which 218 are known to have leaked credentials,
without a single workflow file changing (counts are vendor incident telemetry). Tag pinning is a naming
convention, not a control. Pin by trust class instead:

| Trust class | Pin | Rationale |
| --- | --- | --- |
| Third-party / community steps | **Full commit SHA only** | Mutable tags are attacker-controlled once the repo is |
| Container/build images | **Immutable digest only** | Same mutability, larger payload |
| Platform-vendor first-party steps | Tag pin **permitted** *if* recorded in the profile with a reason | Vendor-operated namespaces have a different threat model; the exemption must be a written decision, not a habit |

The allowlist is a closed set: a SHA pin to an action nobody approved is pinned malware. A SHA pin MUST
carry a version comment so updates stay reviewable, and MUST be bumped by the same bot flow as
dependencies — bumped by hand it escapes §2.1's cooldown, so a step that looks immutably pinned can be
moved to a commit published an hour ago.

**Migration ramp.** Retrofitting this to an existing workspace fails if it starts blocking. Declare in
the profile an **advisory period** with a start date and an explicit end date: during it, existing
unpinned steps are reported but do not fail, while *new* violations fail from day one; at the end date
the check becomes **blocking** for everything. A ramp with no end date is a permanently advisory check
— a report nobody reads. The same shape applies to §5.1 and §5.3 in a live pipeline.

### 3.2 The pipeline's own token defaults to read-only and is widened per job

The credential the pipeline grants its own steps MUST default to **read-only for the whole pipeline** and
be widened only on the job that writes, declared in the pipeline definition rather than inherited from a
platform default (e.g. a top-level workflow `permissions:` block, a job-token allowlist, or the
equivalent named in the profile). An inherited default scope is a write-capable credential handed to
every step in §3.1's trust chain, including the one that gets compromised. Scope secrets to the
consuming job for the same reason.

### 3.3 Untrusted event data never reaches a shell

Attacker-controlled event fields — branch names, PR titles and bodies, issue text, commit messages,
author names — MUST NOT be interpolated directly into a shell step. Template interpolation happens
**before** the shell sees the script, so a crafted title becomes a command in the runner's context,
with its token and its secrets. Pass such values through a quoted environment variable or an explicit
step input. This is the script-injection half of CICD-SEC-4, and it is statically detectable.


### 3.4 Workflows triggered by outside contributions get no secrets and no write scope

**Applies when:** the repository accepts contributions from outside the trust boundary — a public repo,
or forks from outside the organisation. A workspace with no such surface records that in the profile
and the rule is satisfied.

Such a pull request is attacker-authored code the pipeline runs on request: the compromise needs no
dependency, no tag move and no credential theft, just a PR. These runs MUST therefore execute with **no
secrets and read-only scope**, on the trigger that runs the contribution's code in the *contributor's*
context rather than the one that runs it against the base repository's secrets — the two triggers are
typically one word apart, so the profile names the correct one. Jobs needing credentials against outside
code run only after a human approval gate, where the reviewer approves **the commit SHA they read**, not
the branch, because the branch moves.

### 3.5 The pipeline's own definition is inside the trust boundary

The workflow definition is code that runs with the pipeline's privileges, so it is protected at least
as strongly as the code it deploys: changes to CI config, the pinned allowlist and release workflows
take the same review path as application code, and **the release path MUST NOT be reachable by pushing
directly to the branch it builds from**. Otherwise every control above is one force-push from being
edited out, with no diff anyone read (CICD-SEC-1).

## 4. Build-time identity — no long-lived credentials in CI

*OWASP CI/CD CICD-SEC-2 Inadequate IAM, CICD-SEC-6 Insufficient Credential Hygiene.* **The question is
not conditional:** every credential the pipeline holds is enumerated in the profile, wherever CI exists.

### 4.1 Static cloud and registry credentials are replaced by federated short-lived identity

A long-lived deploy key or publish token stored in CI never expires usefully, is readable by every step
in that job (§3.1), and survives any log or exfiltration that catches it once. Every cloud and registry
integration MUST use **workload identity federation where the provider offers it** — the runner
presents a short-lived, workload-bound OIDC token, the provider exchanges it for minutes-long
credentials — and publishing uses the registry's trusted-publishing flow where one exists (e.g. npm
trusted publishing; §0).

Providers with no federation path are common: a host reached over SSH, a store-submission key, a
self-hosted registry, a platform deploy hook. That is **not** a violation. It is a static credential
that MUST carry a rotation interval and an expiry date in the profile's build-identity table, whose
`Waiver + expiry (if static)` column *is* the waiver record (§6.1). What fails is a static credential
nobody wrote down and nobody dated.

### 4.2 The trust condition names organisation AND repository AND ref or environment

Federation is only as strong as the subject condition on the provider side. A condition matching the
organisation alone trusts **every repository in it — including one an attacker who obtains any
repo-creation ability can create** — and every branch in them. The condition MUST pin at minimum org +
repo + (ref or deployment environment); production deploys SHOULD pin the **environment**, so a workflow
on an arbitrary branch cannot assume the production role. A wildcard is a profile-recorded decision.

### 4.3 The publishing identity is a workflow, not a person

Release publication MUST authenticate as the pipeline, not as a maintainer's account. A personal token
used for releases makes one person's laptop, session and inbox part of the release path — and the 2025
npm worm (§2.4) propagated on exactly that. Human accounts retaining publish rights MUST carry MFA and
be enumerated in the profile: an unenumerated one is a release path nobody rotates (§6.3).

## 5. Artifact provenance and inventory

**Applies when:** an artifact crosses a trust boundary between the system that built it and the system
that runs or consumes it — another team, another repo, a customer, a separate deploy target. A workspace
whose platform builds and deploys inside one trust domain records that in the profile and §5 is met;
"no released artifacts" is a valid single row.

### 5.1 The SBOM is a generated build output with a drift check, never a maintained document

An inventory of components MUST be **generated by the build from the resolved dependency graph** and
published alongside the artifact, in a machine-readable standard format (e.g. CycloneDX 1.7 or SPDX
3.0.1) with the format version recorded. A hand-maintained inventory is stale by the second release,
and a stale inventory answers "are we affected?" wrongly and confidently — worse than none, because
someone believes it. It records component + version + resolved location for at least all direct
dependencies; the vulnerability scanner (`security.md` §10) consumes it, and neither replaces the other.

CI MUST fail when the generated inventory **drifts** from the committed lockfile-derived graph. Compare
the **normalised component set** — name + version + resolved location, sorted — excluding document
identity and timestamp fields (serial number, namespace, creation time), which change on every
regeneration. A byte-diff is red on a clean tree, and a gate red on a clean tree is deleted, not met.

### 5.2 Released artifacts carry signed provenance at a declared SLSA build level

Each published artifact MUST be accompanied by **signed build provenance** — an attestation binding the
artifact's digest to the source revision, the builder identity and the build parameters (e.g.
Sigstore-backed artifact attestations, or npm `--provenance`). The profile declares the **target SLSA
level with its track and spec version**, and what is missing for the next one: "we do SLSA" is not a
claim anyone can check; "SLSA v1.2 Build L2" is. Provenance is generated by the *build platform*, not
by a step the build can be tricked into skipping — a self-attesting build attests to the attacker.

### 5.3 Consumers verify fail-closed against an expected signer identity

An attestation nobody verifies is metadata. Every consumer — deploy job, downstream repo, runtime image
pull — MUST verify before use, and MUST **fail closed** when verification fails or when the attestation
is absent. It MUST assert an **expected signer identity**, not merely "a valid signature exists": any
identity in the world can produce a valid signature over anything. With Sigstore tooling that means both
`--certificate-identity` (or its regex form) **and** `--certificate-oidc-issuer`; with platform-native
verification, constraining the owner or repository it must come from. A verify step that passes on an
unsigned artifact is decorative, and that is how this control is usually broken.

## 6. Exceptions, posture, and regulatory triggers

### 6.1 Every exception is a dated waiver with an expiry, in one named register

An unpinned step, a static credential, a skipped cooldown, a scanner finding accepted for a release: each
MUST be an explicit waiver recording **what, why, who accepted it, and the date it expires**. Expiry is
what distinguishes a waiver from a decision nobody revisits. **One register, named in the profile:**
where the workspace already runs a security-exceptions list or risk register, use it and record its
location; otherwise the profile's waiver table (Appendix A) *is* the register. A second register is a
second thing to go stale, and an escape hatch pointing at a register that does not exist is unusable —
the gate gets deleted instead of waived.

### 6.2 A posture score is tracked, not chased

Where an automated posture check runs (e.g. OpenSSF Scorecard, whose `Pinned-Dependencies`,
`Token-Permissions` and `Dangerous-Workflow` checks map onto §3), its value is the **per-check finding**,
not the aggregate. Wire the individual checks into CI; treat the composite as a trend, never a target —
optimising an aggregate moves the number and not the risk. Judgement-bounded: no threshold on the
composite is defensible as a merge gate.

### 6.3 Compromise response assumes every secret the runner could read is disclosed

When a dependency, action or image in the pipeline is found compromised, the response MUST be: rotate
**every** credential reachable from the affected jobs (not only those you believe were used), review the
audit log for publishes and deploys in the exposure window, and check whether any artifact built then was
released. Partial rotation is the failure shape. Enumerate "reachable from this job" in the profile
*before* the incident; under pressure a credential family gets missed (`security.md` §6 owns blast radius).

### 6.4 A regime that reaches the build becomes build obligations, not a second register

Some adopting workspaces ship products in scope of regimes imposing supply-chain obligations directly.
The generic trigger for the **EU Cyber Resilience Act** (Regulation (EU) 2024/2847): placing a *product
with digital elements* on the EU market as its manufacturer. Applicability is recorded once, in the
sibling register named in §0 — not here. Where it applies, the obligations land in this lane. Annex I
Part II point (1) requires manufacturers to "identify and document vulnerabilities and components
contained in products with digital elements, including by drawing up a software bill of materials in a
commonly used and machine-readable format covering at the very least the top-level dependencies of the
products" — which §5.1 already produces and whose drift check keeps true. Article 14 imposes reporting
duties (from 2026-09-11; the rest from 2027-12-11) whose clocks start when the manufacturer **becomes
aware** of an actively exploited vulnerability or severe incident: early warning within 24 hours, fuller
notification within 72. That clock presumes §6.3's blast-radius table already exists.

A recorded *"no, because the product is not placed on the EU market as a product with digital elements"*
is a complete answer; an unrecorded answer is the finding. This standard states no verdict about any
organisation's obligations, and an agent loading it MUST NOT infer one.

## Failure shapes

Named patterns — recognise one, cite it by name.

- **The off-by-a-thousand cooldown.** A cooldown is configured, reviewed and merged — against the wrong
  key or unit, so `7` buys seven minutes instead of a week, or an older pinned manager ignores the key
  entirely. The control reads as adopted in every review. (§2.1)
- **The tag that moved.** Every step is version-pinned and nothing in the workflow files changes, but the
  tags now point at a malicious commit and the runner dumps its secrets next push. (§3.1)
- **The package that never existed.** An assistant suggests a plausible dependency name, nobody resolves
  it, and someone waiting for exactly that has registered it. It installs cleanly; that is the point. (§2.2)
- **The decorative verify step.** A verification step that logs a warning and exits zero when the
  attestation is missing or the signer is unexpected — sibling of the inventory hand-maintained at
  release one and cited in an incident at release nine. Both green, both wrong. (§5.1, §5.3)

## Checklist

Decidable from the diff alone, before merging:

- [ ] New dependency: does the PR body or commit record the registry resolution (exact name found,
      source repo resolving, publishing history), is the name not a near-variant of a popular one, and
      does it land in its own commit so the lockfile diff is reviewable?
- [ ] Cooldown present, in a committed repo-scoped file, with the **right key and unit** for this
      manager, and the manager version pinned high enough to honour it?
- [ ] New install-script allowlist entry states why that package must build; every new/changed CI step,
      image and runtime-fetched tool is pinned per its trust class (SHA or digest) and on the allowlist,
      with any vendor tag-pin exemption recorded in the profile?
- [ ] Pipeline declares a read-only default token scope widened only on the job that writes, and no
      untrusted event field (title, body, branch, author) reaches a shell step?
- [ ] No **new** static cloud/registry credential — or, if unavoidable, it lands in the profile's
      build-identity table with a rotation interval and an expiry date? Any federation trust condition
      changed here names org + repo + ref/environment, no bare wildcard?
- [ ] Release-affecting change: SBOM still generated by the build and drift-checked, and any new
      consumer verifies **fail-closed against an expected signer identity**?
- [ ] Every exception here is a dated, expiring waiver in the register the profile names?

## Guard rails

**Each is mechanizable.** `[tool]` marks one an off-the-shelf tool class does; `[script]` marks one the
workspace writes itself, in tens of lines — a list hiding its build cost is ignored by run five.

- **[supply-chain-and-build-integrity.GR1]** `[tool]` **Workflow static analysis for pinning, permissions and injection** — a CI-configuration linter (e.g.
  `zizmor`, `actionlint`, Semgrep CI-YAML rulesets) on every workflow-file change. Advisory during the
  declared ramp (§3.1), blocking at its end date.
- **[supply-chain-and-build-integrity.GR2]** `[tool]` **SBOM regenerate-and-diff** — regenerate the inventory in CI (e.g. Syft, CycloneDX generators) and
  diff the **normalised component set** (§5.1); a silently failing generator is otherwise
  indistinguishable from success.
- **[supply-chain-and-build-integrity.GR3]** `[tool]` **Provenance verification in the deploy job, asserted by a negative test** — verification runs
  fail-closed, *and* a test feeds it an unsigned or wrong-identity artifact and asserts a non-zero exit.
  A verify step nobody has ever seen fail is untested code in the trust path.
- **[supply-chain-and-build-integrity.GR4]** `[script]` **Cooldown assertion test** — reads the committed manager config and asserts key name,
  unit-appropriate value and pinned manager version together. A wrong-unit value is syntactically
  perfect, so this is the only mechanical defence against §2.1's shape.
- **[supply-chain-and-build-integrity.GR5]** `[script]` **Allowlist diff check** — assert every referenced step, image and runtime-fetched tool resolves to a
  SHA or digest on the committed allowlist; a pin to an unapproved source fails though it is pinned.
- **[supply-chain-and-build-integrity.GR6]** `[script]` **Lockfile-diff gate** — flag any pull request whose lockfile adds a package absent from the manifest
  diff, plus a check that the install command runs with scripts disabled.
- **[supply-chain-and-build-integrity.GR7]** `[script]` **Waiver expiry and static-credential report** — a scheduled job reading the profile's waiver and
  build-identity tables that fails when an entry passes its date: repo state, not diff state.

*Judgement-only, stated as such:* whether a vendor step deserves a tag-pin exemption (§3.1), whether an
install-script justification is real (§2.4), and what composite posture score is acceptable (§6.2) are
review decisions. No tool decides them.
