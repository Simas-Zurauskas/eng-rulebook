# API Contracts & Codegen Standard

> **Type:** Generic, reusable standard · **Rev:** 1 (2026-07-17)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
>   Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs the HTTP contract between an API and its consumers: where the spec lives, the
> response envelope and error-code vocabulary, how client types are generated, and the
> HTTP-level facts — status classes, mount order — that are part of the contract whether or
> not the spec mentions them. Core idea: **one authoritative contract source; everything
> else derived mechanically, and re-derived every time the source changes.**

## 0. Scope — when this standard applies

Any service exposing an HTTP API consumed by sibling repos. Assumed context: a multi-repo
TypeScript workspace — backend API, web client(s), mobile app, worker(s) — with docs
generated by wiki-system and client types code-generated from a runtime API spec
(e.g. OpenAPI **3.1.x** consumed by `openapi-typescript`, which does not yet read 3.2 —
the spec version is a *generator-constrained* choice, pinned in the profile, not a default).

Owned elsewhere — cross-reference, don't restate:

- What makes spec-feeding text machine-consumed, and its truthfulness bar:
  `comment-standard.md` §3.1, §4.3.
- Runtime validation internals (schema-derived types, boundary parsing): `type-safety.md`.
- Environment-gating mechanics and boot guards: `config-and-environment.md`.
- Rate-limit and auth *policy*: `security.md` — this file owns only their **topology**
  (where they mount, and what a route silently inherits or escapes).
- Correlation-id logging and alerting: `observability.md` — this file owns the id's
  presence on the wire.

**External anchors** — name + version + status, never URLs. *Anchors verified 2026-07-28;
re-verify anything older than 12 months (`_authoring.md` rule 6).*

## 1. Core principle

An API contract is **everything a consumer can observe and depend on**: the spec document,
the envelope shapes, the error-code vocabulary, status classes, idempotency and pagination
semantics — and the middleware topology that decides which routes are limited, parsed, and
gated. Every one of these MUST have exactly one authoritative source; every other
representation (generated types, client branches, served docs) MUST be derived from it
mechanically and checked for staleness mechanically.

Two corollaries drive the rules below:

1. **Anything hand-mirrored drifts, and contract drift fails silently** — both sides
   compile, both test suites pass, production disagrees.
2. **Generated artifacts are shipped build output.** They do not update themselves when the
   source is fixed; a stale generated file carries the old lie into every consumer until
   someone re-runs the generator.

## 2. One source of truth, stated

Pick exactly one mode per project and record it in the project profile (Appendix A):

- **Spec-from-code** — the spec is assembled at runtime or build from doc blocks and schema
  modules in the API source (e.g. `swagger-jsdoc` scanning controller JSDoc) and served
  over HTTP. There is **no committed spec file**.
- **Code-from-spec** — a committed spec file (e.g. authored in TypeSpec, emitted as
  OpenAPI 3.1.x) is the source; server stubs and client types generate from it. Record the
  emitted spec version, not just "OpenAPI" — every consumer's generator has a version ceiling.

Rules, in either mode:

- **State the mode.** Unstated, an agent treats whatever spec-shaped file it finds as the
  live contract — in one audited workspace the only spec file on disk was a read-only
  artifact of a retired legacy stack.
- **Spec-from-code: the generator's include glob is part of the contract, CI-guarded.**
  A spec doc block outside the glob is **silently dropped** — no error, no warning; the
  endpoint exists and works, and is invisible to every consumer's codegen. Observed: the
  generator scanned only the controllers directory, so a block placed in a routes file
  never reached either client.
- **Wire enums are re-exported from domain code into the spec, never redefined.** A
  redefinition is a second source of truth. Observed good practice: every enum in the
  document — including the error-code set — imported from the model layer, so the spec and
  the DB definitions structurally cannot diverge.
- **Undocumented surface is deliberate and listed.** Endpoints intentionally absent from
  the spec (debug, machine-to-machine, server-rendered pages) have no generated client
  types; list them in the profile so their absence reads as design, not omission.

## 3. The envelope: uniform and closed

One success shape, one error shape, **no third shape anywhere** — e.g.
`{ data: <payload> }` on success and `{ data: null, error: { code, message, requestId } }`
on failure: a machine code, a human message, a correlation id.

- **Clients branch on `code`, never on `message`.** Message text is for humans and logs;
  branching on it turns copy edits into breaking changes.
- **The code set is closed and enumerated**: declared once, exported into the spec as an
  enum, and enforced at every emit site so an unlisted literal is a compile error (e.g. a
  TypeScript `satisfies`-checked union). **Adding a code is a contract change** — spec
  change plus regeneration in every consumer.
- **No phantom vocabulary.** Every code has at least one live emit site. Observed: three
  codes whose flow had been deleted survived in the closed set and shipped in both
  clients' generated unions, inviting dead branches.
- **Every error response carries the correlation id — including middleware-emitted ones.**
  Observed: auth middleware hardcoded a null id in the body on the API's highest-volume
  error class, breaking body-side correlation exactly where it was needed most.
- **Position relative to RFC 9457 (Problem Details for HTTP APIs; obsoletes RFC 7807):**
  RFC 9457 is this rule's standardised cousin — its `type` is the machine code, `title` /
  `detail` the human text, `instance` and extensions the correlation. Adopting it
  wholesale is the right default for a public API. A custom envelope is legitimate inside
  a closed workspace **provided it delivers the same three guarantees uniformly**. What is
  never acceptable is per-endpoint error shapes.

## 4. Enums on the wire

- **Any finite vocabulary crossing the wire MUST be declared as an enum in the spec**, so
  that adding or renaming a member becomes a type error in every consumer at next regen.
  Observed counterexample: a preset-catalog id declared as a plain `string` on the wire
  while two repos each rebuilt the catalog from their own constants — codegen was
  structurally unable to catch drift, and a mismatched id was a runtime rejection.
- **A deliberately open string field is documented in the profile with the reason**, and
  gets a runtime guard at the boundary instead (guard internals: `type-safety.md`).
- **Declare only states that are produced.** An enum member nothing ever emits (observed: a
  status in a four-state union no code path wrote) makes every client handle a fiction.
- **Looseness defeats the check.** `additionalProperties: true` and friends let a wrong
  documented shape survive codegen — observed: an output documented with URL fields while
  the implementation wrote storage keys; no consumer type error resulted.

## 5. Codegen workflow and generated-file discipline

- **After any shape change, regenerate in EVERY consumer — never just one — from the same
  running spec (or committed file).** The observed incident: a falsehood in spec
  descriptions (a delivery mechanism that did not exist) propagated into **both** clients'
  generated types and **outlived the source-side fix by weeks**, because codegen was never
  re-run. The generator's output holds whatever was true — or false — at last regen.
- Generated files (e.g. a `src/api/_generated.ts` per consumer) are build output:
  - **never hand-edited** — fix the source and regenerate; a hand edit is destroyed on the
    next regen at best, or silently diverges the client from the wire at worst;
  - **never deep-cited by line number** — lines shift wholesale on every regen; cite
    exported symbol names (comment-standard §5.6);
  - **excluded from lint/format autofix** — an autofixer rewriting build output creates
    permanent phantom diffs;
  - marked as generated (header comment + ignore-file entries).
- **CI catches staleness by regenerating and diffing** (Guard rails). Manual discipline
  demonstrably fails — that is the incident above.
- **Record each consumer's codegen prerequisites in the profile** (e.g. "requires the API
  and its DB running locally"). An undocumented prerequisite is why regeneration is
  skipped "just this once".

## 6. Spec text ships to consumers

Endpoint descriptions, summaries, and schema `description:` strings are not comments —
they are build input that lands verbatim in other repos' generated artifacts and rendered
docs. Comment-standard §3.1 owns the classification; comment-standard §4.3 owns the
truthfulness bar.
This file adds the contract-side consequences:

- **Truthful behaviour statements only** — no fictional mechanisms (the shipped-lie
  incident was exactly this), no aspirations, no archaeology.
- **No internal references** — wiki paths, planning docs, issue links do not belong in
  text that ships beyond the repo. Self-contained or absent.
- **Say what a caller needs**: side effects, idempotency, pagination, and which error
  codes this endpoint can actually return.

## 7. Evolution

- **Additive-optional first.** New optional fields, new endpoints, new enum members (with
  regen everywhere) — never rename, retype, or remove in place while any consumer depends
  on it.
- **Breaking changes are coordinated or versioned.** In a closed workspace that owns every
  consumer, lockstep coordination — change, regenerate, fix all consumers in one motion —
  is legitimate and cheaper than versioning. For consumers you don't control, version the
  surface and signal retirement with a real migration window (Deprecation header,
  RFC 9745; Sunset header, RFC 8594).
- **Idempotency semantics are declared in the spec.** If a mutation accepts a client
  idempotency key, the spec states the field, its constraints, and what a replay returns
  (observed good practice: create endpoint idempotent per user + client key; a retry
  returns the original resource as 200, not a second billing as 201). Undeclared
  idempotency is unusable idempotency — no client author dares retry.
- **Pagination contracts are explicit; an unbounded list endpoint is a scaling defect.**
  Observed: no list endpoint accepted a limit or cursor, and one was the client's
  in-flight poll target — every few-second poll re-fetched the user's entire history, cost
  multiplied by poll frequency. Declare limit + cursor (with defaults and maxima) in the
  first version; retrofitting pagination is a breaking change.

## 8. HTTP correctness

- **Correct status class per outcome** (RFC 9110, HTTP Semantics): 400/413/415 for body
  problems, 401 unauthenticated vs 403 unauthorized (clients route one to sign-in and the
  other to an error state — keep them distinct), 404 unknown, 409 conflict, 429 limited,
  5xx only for server faults. A wrong class is not cosmetic: client branches, retry
  logic, and alert thresholds all key on it.
- **The error middleware is the single formatter.** Ad-hoc error `res.json(...)` at call
  sites is how a second error shape is born. Where a middleware must self-respond (rate
  limiters, the 404 catch-all), it MUST emit the identical envelope — pinned by a test.
- **Map library/framework errors to their client-safe status.** Parser and framework
  errors carry a status the formatter must honour: pass a library 4xx through; scrub a
  library 5xx to a generic 500. Observed failures: malformed JSON surfaced as a scrubbed
  `500 INTERNAL_ERROR`, and a CORS rejection thrown as a plain error did the same.
- **Guard `headersSent`.** An error thrown after a streamed response has begun must be
  delegated (e.g. Express: `if (res.headersSent) return next(err)`), never re-written —
  otherwise the formatter itself crashes the response mid-stream.
- **A promised code must be emittable.** If the spec promises `409 <CODE>` on duplicate,
  the concurrent path must produce it. Observed: check-then-write against a unique index
  let the racing duplicate surface as a scrubbed 500 while the spec promised a 409.
- **Unknown paths return the envelope**, not the framework's default HTML 404.

## 9. Mount order is part of the contract

Registration order decides which cross-cutting facts apply to which route. A reader MUST
be able to derive, for any route: its auth gate, its rate limiter, its body-size limit,
and whether a correlation id exists by the time it can fail.

- **A route mounted above the limiter and parsers silently inherits neither.** Observed
  both ways: a router deliberately mounted above the global limiter (so its traffic
  wouldn't drain the shared budget) while its own header comment claimed the opposite —
  and the same router mounted a *second* time below, dead code that invited exactly the
  wrong "cleanup" (deleting the live mount).
- **Order the chain deliberately:** correlation id + logging before anything that can
  fail (observed: a parser mounted before the request-id middleware produced the one error
  class with no correlation id); limiters before body parsers, so a flood is throttled
  before it is buffered and parsed; parsers before routers; catch-all routers last so they
  can never shadow an API route; the error formatter after everything.
- **Gates are router-level facts, applied once at the mount** — not re-applied per
  handler. A per-handler re-check hides the real gate from readers and drifts.
- **Body limits are per-route decisions, not one global.** A single global limit sized for
  the largest admin payload hands every public route the same pre-auth buffer-and-parse
  exposure (observed: a 50 MB global parser reachable unauthenticated on every path).
  Size per route, and keep the largest in lockstep with the reverse proxy's body cap —
  a mismatch produces production-only 413s that dev never reproduces. Record both in the
  profile.
- **Environment-inert gates are tested with the environment forced.** Observed: every rate
  limiter skipped outside production, so no local run can validate one — a passing dev
  loop proves nothing (gating mechanics: `config-and-environment.md`).

## 10. Non-production spec surfaces

- **The spec endpoint and its UI are env-gated off in production** (mechanics:
  `config-and-environment.md`): the served document enumerates your surface for attackers,
  and codegen is the only consumer that needs it. Consequence: **codegen targets a
  non-production instance by definition** — record the target in the profile.
- **Health and version endpoints are always on, in every environment** — they are the
  production-safe probes. Their shape may deliberately sit outside the envelope (e.g.
  plain-text health); if so, say so in the profile rather than letting it read as a bug.

## 11. Request bodies are closed contracts

*OWASP API Security Top 10 **API3:2023 Broken Object Property Level Authorization**; ASVS 5.0
V15 Secure Coding and Architecture (its defensive-coding section covers mass assignment).*

The runtime half is `security.md` §5.1 — every body parsed by a schema at the route boundary,
nothing a schema didn't admit. This file owns the **documented** half, and the two drift
independently: a server can enforce a closed shape while the published contract says otherwise,
and every consumer generates against the contract.

- **Every request-body schema MUST declare a closed property set** (e.g.
  `additionalProperties: false`). Open, the contract states what the endpoint *tolerates* rather
  than what it *accepts*, and codegen turns that into a consumer type permitting fields the
  server never promised — so a later tightening is a breaking change nobody can date, because no
  version of the spec ever said the field was out. §4's looseness rule is the codegen-drift half
  of the same fact; this is the acceptance half.
- **A request schema MUST NOT declare a server-controlled property as writable** — role,
  owner id, balance, verification flags, lifecycle status. Those are outputs of a server
  decision; listing one on the write surface documents a privilege-escalation path as a feature,
  and the client type generated from it invites callers to send it.
- **Model the write surface as its own schema.** Reusing the response schema as the request
  schema is how the previous rule gets violated silently: every server-controlled field the
  response legitimately returns becomes documented as accepted input at the next regen.

## Failure shapes

Named patterns from real audits, genericised:

- **The dropped block.** A spec doc block sits outside the generator's include glob.
  Nothing errors; the endpoint works; no consumer type is ever generated. Discovered only
  when a client developer asks why the endpoint "doesn't exist".
- **The shipped lie.** A false statement enters spec descriptions, propagates through
  codegen into every consumer's generated artifacts, and outlives the source-side fix by
  weeks — nobody re-ran codegen, and generated files hold whatever was true at last regen.
- **The phantom vocabulary.** Error codes or enum members with zero emit sites ride the
  closed set into every client union: dead branches, misleading audits, noise re-shipped
  by every regen.
- **The open-string drift.** A finite catalog id crosses the wire as a plain string; each
  repo maintains the vocabulary independently; the mismatch is a runtime rejection that
  codegen was structurally unable to catch.
- **The scrubbed 4xx.** A framework error (malformed body, CORS rejection) reaches the
  formatter without a recognised status and ships as a generic 500 with the useful message
  scrubbed — and no correlation id, if the id middleware mounted too late.
- **The shadow mount.** A route mounted above — or twice around — the cross-cutting
  middleware. It silently escapes the limiter and parsers, or is dead code inviting
  deletion of the live mount; the comment claims one topology, registration order ships
  another.
- **The unbounded poll.** A list endpoint with no limit or cursor becomes the client's
  poll target; response size grows linearly with history, multiplied by poll frequency —
  a designed-in scaling cliff on the hottest read path.

## Checklist

Before merging an API change:

- [ ] Contract-source mode stated in the profile; any new spec block inside the glob?
- [ ] Wire enums re-exported from domain code; new codes added to the closed set?
- [ ] Every declared code/enum member has an emit site — and vice versa?
- [ ] Codegen re-run in EVERY consumer; diffs committed; zero hand edits to generated files?
- [ ] Spec descriptions truthful, self-contained, free of internal refs (comment-standard §3.1)?
- [ ] Change additive-optional — or coordinated/versioned with deprecation signalled?
- [ ] Mutations: idempotency declared in the spec? Lists: limit + cursor declared?
- [ ] Correct status class per outcome; all error paths through the single formatter;
      self-responding middleware emits the identical envelope?
- [ ] New route's real mount position checked — which limiter, parser limit, and auth gate
      does it actually inherit?
- [ ] Per-route body limits within the reverse proxy's cap?
- [ ] New/changed request body: property set closed in the spec, and no server-controlled
      field (role, owner id, status, balance) declared writable — including via a schema
      shared with the response?

## Guard rails

CI checks that make this standard enforceable rather than aspirational:

- **[api-contracts-and-codegen.GR1]** **Glob guard** — fail on spec doc-block markers found outside the generator's configured
  glob. Closes the dropped block.
- **[api-contracts-and-codegen.GR2]** **Staleness gate** — boot the API (or read the committed spec), run every consumer's
  codegen, then `git diff --exit-code` the generated files. Closes the shipped lie.
- **[api-contracts-and-codegen.GR3]** **Vocabulary liveness** — assert every error code / enum member has ≥1 emit site
  (grep- or test-based). Closes the phantom vocabulary.
- **[api-contracts-and-codegen.GR4]** **Envelope conformance suite** — drive the 404 catch-all, malformed JSON, oversize body,
  unauthenticated, unauthorized, and rate-limited paths; assert envelope shape, status
  class, and correlation id on each. Pins the single formatter, the self-responding
  middleware, and the middleware order in one suite.
- **[api-contracts-and-codegen.GR5]** **Mount-order pin** — a test asserting the app's actual topology for the escapes (routes
  above the limiter, per-route parser limits), so a re-order fails a test instead of
  production; run environment-inert gates with the production flag forced.
- **[api-contracts-and-codegen.GR6]** **Generated-file hygiene** — generated paths in lint/format ignore lists, plus a check
  that no commit modifies them except alongside a codegen run.
- **[api-contracts-and-codegen.GR7]** **Description lint** — reject internal doc paths in spec text (shared with
  comment-standard's reference guard).
