# Performance & Data Access Standard

> **Type:** Generic, reusable standard · **Rev:** 2 (2026-07-28)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
> Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs how fast and how cheaply the system reaches its data: query shapes and the indexes
> that back them, the N+1 class, result and payload bounds, caching, pool sizing, and latency
> budgets. Core idea: **a performance defect is not slow code — it is a cost that scales with
> an input you do not control, and it ships green because your fixtures are small.**

## 0. Scope — when this standard applies

Applies to every read or write path whose cost varies with data volume: API handlers, list endpoints,
dispatcher and sweeper queries, aggregation jobs, and clients polling them. Assumed context (per
`_authoring.md`): a multi-repo TypeScript workspace — a backend API that owns persistence, web
client(s), a mobile app, worker(s) — with docs generated by wiki-system and client types code-generated
from a runtime API spec.

**Owns:** index justification and query-shape matching, compound key order, the N+1 class, result-set
bounds and server-side page-size enforcement, payload size and memory amplification, in-store vs
in-memory sort/aggregation, cache key/TTL/stampede design, pool sizing, latency budgets and deadline
cancellation.

**Does not own** (one-line cross-refs only):

- *Correctness of stored state* — atomic claims, fencing, idempotency, TTL cleanup, cascades:
  `data-integrity.md`. That file owns whether the write is **right**; this one owns whether reaching it
  is **affordable** — every index, N+1 and payload-placement question included.
- *Behaviour when a dependency **fails*** — timeouts, retry, ladders, bulkheads: `resilience.md`. Slow
  is this file; broken is that one. Deadline **propagation** and inner-shorter-than-outer ordering are

- *The pagination **contract*** and the unbounded-list failure shape — `limit`/`cursor` and their maxima
  in the spec: `api-contracts-and-codegen.md`. This file enforces the bound in the query itself.
  *Emission mechanics* — metric shape, alarm bindings, the silent-degradation ban: `observability.md`;
  this file says **what to measure**.
- *How a point-of-edit comment is written* — `comment-standard.md` §3.2 (this file requires index↔query
  traceability, not its form). *Body-size limits as an abuse control* — `security.md` §5.2. *The waiver

## 1. Core principle — review the growth curve, not the millisecond

Every defect in this lane answers two questions, and a change that cannot answer them is not reviewed:

1. **What input grows?** Rows per user, items per list, bytes per record, requests per second,
   concurrent viewers of one cache key.
2. **What does the cost do when it grows?** Constant, linear, quadratic — or *cliff*, where the
   system works exactly as designed until a threshold and then stops entirely.

The cliff is the dangerous one: invisible to every pre-production signal, because the only variable that
moves is data you do not control (§2.2 is the worked example). Corollary: **an unbounded query is a
latent outage whose trigger date is set by your users, not your release schedule** — so bounds are
structural, in the query.

## 2. Query shapes and indexes

### 2.1 An index is justified by a query shape, never by intuition

Every index MUST be traceable to a **named query shape** — a specific filter + sort + projection some
code path issues — and the trace MUST be readable at the declaration site (`comment-standard.md` §3.2
owns its form). Traceability runs both ways: an index nobody can attach to a query is deleted by someone who
cannot tell it is load-bearing, and every declared index taxes every write whether or not anything reads
it. The expensive inverse is §2.2.

### 2.2 Index the sort, not only the filter

**Every claim and sweep query MUST have a backing index that includes its sort key** ("covering", in
§2.4's sense, is a further optimisation, not what is required here). More generally, **any** query whose
ordering is not served by an index blocking-sorts the full candidate set; some engines abort past a
memory budget (an availability cliff), some spill to disk (a latency cliff), and read-modify-write claim
commands typically expose no spill option at all.

The failure prevented, from one audited multi-repo TypeScript workspace: a dispatcher claimed work
sorted by creation time with no index behind the sort, over documents embedding base64 media (~10 MB
worst case). Draining a backlog cost O(N²) full-document fetches, and past the store's ~100 MB budget
**every claim aborted and the pipeline stopped, permanently** — at the seasonal peak that created the
backlog.

### 2.3 Compound-index key order follows the query; design against the prefix rule

A compound index serves a query through a **left-to-right prefix** of its keys: `(a, b, c)` serves
filters on `a`, `(a, b)`, `(a, b, c)`. Treat that as the portable default and **the only thing to design
against** — a new query filtering on a *suffix* of an existing index looks covered and is not. Some
planners use a non-leading column when the leading one has very few distinct values (e.g. PostgreSQL 18
B-tree skip scan, MySQL 8.0.13+ skip scan): an escape hatch you confirm in a plan (§2.5), never one you
design for or assume in review. Key order follows the predicate class — equality keys first, then the
sort key, then range keys (e.g. MongoDB's ESR guidance; a range predicate consumes the ordering the sort
needs).

### 2.4 Cover the read where the read is hot

Where a hot query reads only a few fields, prefer an index that **contains** those fields so the read is
answered from the index alone (e.g. PostgreSQL `INCLUDE` non-key columns driving an index-only scan).
Prevents the shape where an index correctly finds 20 rows and then issues 20 random record fetches —
§3's N+1, relocated into the storage layer where it is harder to see.

### 2.5 How you know: read the plan

**Applies when** the store exposes a plan command and a seeded environment with representative data
exists. Index claims are then verified against the engine's **execution plan**, never the code (e.g.
`EXPLAIN (ANALYZE, BUFFERS)`): intended index chosen, rows examined close to rows returned, no
blocking-sort stage, no full scan on a growing table. Otherwise the profile records the shape as
**key-schema-verified** or **inferred**, and §2.6's label becomes mandatory.

### 2.6 A static read cannot observe index usage — say so

A diff tells you an index is *declared* and a query is *written*. It does **not** tell you the planner
chose it, or that it exists in the production database at all. Any "this query is unindexed" reached
without a plan is **inferred, not observed**, and MUST be reported that way — preventing the confident
false finding that discredits a whole report. Corollary: a declared index that no migration or startup
assertion creates is not an index.

## 3. The N+1 class

### 3.1 No per-item query in a loop over a list you just fetched

A path that has already fetched a list MUST NOT issue one query per element. Resolve related data in a
single round trip — a set-membership filter over the collected keys (e.g. `$in`, `WHERE id = ANY(...)`),
a join, or an embedded projection the list view reads directly. An endpoint whose query count scales
with its result count is a scaling defect on the same axis as an unpaginated list, and the two multiply
into a cost quadratic in a user-controlled number.

### 3.2 The lazy-load N+1 is the same defect with the loop hidden

An ORM/ODM relation resolved on property access issues its query at the point of *use*, not of *fetch* —
so the triggering loop can sit in a serializer, a response mapper, or a resolver layers away. "Where is
this relation populated?" is therefore a **required review question** for any handler returning entities
with relations, and the answer MUST be an explicit eager load/join/batch at the fetch site: otherwise
the code reads as one query and the database sees one plus the page size.

### 3.3 N+1 hides in fixtures and appears in production

A suite whose fixture has three rows executes four queries where production executes three thousand and
one — passing, fast, silent. So tests for a collection endpoint assert a **query count**, not only a
response body (`testing.md` owns suite hermeticity); it is the only cheap check that survives a refactor
reintroducing a lazy load. Where one is impractical the fixture MUST be large enough that a per-row
query shows in timing.

## 4. Unbounded results

### 4.1 Every collection-returning path is bounded by construction

Every endpoint, query, and job step returning a collection MUST carry a limit **in the query itself** —
a page size, a cursor window, or an explicit cap — from its first version. "All of the user's X" is
correct on the day it ships and is the outage on the day one user has two hundred thousand of them. The
spec-side obligation and its evidence are `api-contracts-and-codegen.md`'s (its *unbounded poll* shape);
this rule is the enforcement, in the query, on the server.

### 4.2 Over-maximum page size is declared behaviour, never a default

A caller-supplied page size above the declared maximum MUST be handled by a **declared** rule — clamp to
the maximum, or reject with the API's out-of-range error — recorded in the spec
(`api-contracts-and-codegen.md`) and in the profile. What is never acceptable is *honouring* it: an
unvalidated `limit=100000` turns a paginated endpoint back into an unbounded one, §4.1's outage through
the front door. Both answers cost something, which is why the choice is written down rather than
defaulted.

### 4.3 Internal and background queries are bounded too

Sweepers, reconcilers, migrations, exports, and admin tooling read the *same* growing tables with none
of an API's traffic shaping, and are the paths most often written without a bound. Every such query MUST
batch with an explicit limit and iterate; an unbounded "find all pending" inside a worker is §4.1's
outage with no rate limiter in front of it.

### 4.4 Deep offset pagination is a second unbounded cost

Offset/skip pagination costs the engine the offset itself — page 5,000 scans and discards everything
before it, so a bounded page size still yields an unbounded query. Prefer **keyset/cursor** pagination
on an indexed, stable, unique ordering key for anything a client pages deeply or a job iterates; offset
paging is acceptable only where the maximum offset is itself bounded and stated.

## 5. Payload size and memory amplification

### 5.1 Records hold keys; blobs live in object storage

A record that a query scans, sorts, polls, or sweeps MUST NOT carry a large payload inline; blobs belong
in object storage and the record holds a **key**. The reason is amplification rather than any single
read: one fat field makes *every* query touching that collection expensive, including those that never
read it. In that same audited workspace an admin UI polled a multi-MB document every 1.5 s only to
discard the payload field, and the same embedded media made §2.2's backlog drain quadratic.

### 5.2 Projections are the default, not an optimisation

Reads MUST request only the fields they use. Selecting whole records to return four fields pays the full
row cost in I/O, network, deserialization, and process memory — the cost that turns §5.1's fat field
into a fleet-wide problem. A field you never selected also cannot leak (`security.md` owns exposure).

### 5.3 Declare a response-size ceiling per route class, and stream past it

Every route class has a stated maximum response size. Where a response can legitimately exceed it —
exports, reports, archives — the route **streams** rather than buffering, so peak memory is a chunk and
not the whole result. Buffering an unbounded result is a per-request memory multiplier: N concurrent
callers OOM the process. (Request-side body caps: `security.md` §5.2.)

### 5.4 Sort, group, and aggregate in the store — and know its ceiling

Ordering, grouping, deduplication, and aggregation MUST be pushed into the query. Sorting in process
memory converts a bounded engine operation into an unbounded application one and defeats §4's bounds
entirely — you must fetch everything to sort it. Where the work genuinely belongs in the application it
operates on an already-bounded set (§4.1). The store's blocking-operation ceiling, and whether exceeding
it aborts or spills, is §2.2's cliff as a number: record it in the profile and design against it.

## 6. Caching

### 6.1 A key encodes every input that changes the value

A cache key MUST include every input the cached value depends on — identity and authorization scope
included. Prevents the highest-consequence cache defect there is: one user's response served to another
because the key omitted the viewer. Where a response varies by credential the safe default is **do not
share the cache across principals**; a shared entry is a deliberate decision recorded in the profile's
cache table with the reason it is safe.

### 6.2 Every entry has an expiry, or a recorded reason it cannot go stale

No cache entry is written without a TTL — **or** a recorded immutability argument: the key contains a
hash or version of every input, so the value cannot go stale and eviction is by capacity
(content-addressed memos, fingerprinted assets). A TTL is not a tuning knob but the **maximum staleness
the product accepts**, stated at the write site; it prevents the entry that outlives the truth it copied
with nobody able to say by how long. For HTTP-layer caches state `Cache-Control` per RFC 9111 —
`private` for anything scoped to one principal, `no-store` where the value must not be persisted at all
— since an absent header hands the decision to heuristics in every intermediary.

### 6.3 Invalidation belongs to the write path

An invalidation that is a separate follow-up step is one a crash, a throw, or an early return skips.
**The lane split, stated once:** whether the write carrying the invalidation is itself atomic is
`data-integrity.md` §2's; whether a derived copy outlives the record it came from is
`data-protection.md` §4.1's. This file owns the cached shape, its staleness bound (§6.2) and its
regeneration (§6.4). Where invalidation cannot be atomic with the write, the TTL is the backstop and
MUST be sized to the staleness you tolerate, not the hit rate you want.

### 6.4 Protect regeneration against stampede

When a hot key expires, every concurrent request misses and regenerates the same value at once — the
spike lands on the dependency at the moment the cache stops absorbing it. Any key both expensive to
compute and concurrently hot MUST have stampede protection: a single-flight lock so one regeneration
serves all waiters, probabilistic early expiry with each reader refreshing slightly before expiry
(Vattani, Chierichetti & Lowenstein, PVLDB 2015 — no coordination required), or serving stale while one
refresh runs. And jitter the TTL: uniform TTLs on keys written together expire together.

### 6.5 A cache with no hit-rate signal is a guess

Every cache emits hit/miss and, where it matters, eviction and regeneration-latency signals (shape and
alarms: `observability.md`). Prevents the two silent states a cache enters: a hit rate that collapsed
after a key-format change, so the dependency takes full traffic unalerted; and a cache that adds a hop
and nothing else, which nobody removes because nobody can prove it idle.

## 7. Connection pools

### 7.1 Pool size is derived, not defaulted

**Applies when** instance count is bounded and knowable. Every pool (database, HTTP keep-alive, cache
client) then has an explicit maximum derived from the other side: the store's connection ceiling divided
across every process that connects to it, workers, migrations and admin tooling included. Prevents both
ends — a pool too small silently serialises a concurrent workload behind a queue nobody watches (§7.2),
and pools summing past the server's limit make **every** instance fail to connect during a scale-out,
when instance count is briefly highest. Where instance count is *not* bounded (per-request or autoscaled
compute) the control is a **pooler/proxy or serverless driver**, whose ceiling the profile records
instead. Either way the arithmetic is written down; a default nobody chose is not a limit.

### 7.2 Pool waits are a measured, deadlined queue

Acquiring a connection MUST have its own timeout, and time spent waiting MUST be a measured signal
separate from query time. An unbounded acquire wait converts store slowness into unbounded request
latency with a perfectly healthy-looking query-duration metric — the requests are not slow, they are
*waiting to start*. The acquire timeout is part of the request budget (§8.2).

### 7.3 A shared pool is a shared failure domain

One pool serving unrelated workloads means the slowest workload starves the rest: a reporting query
holding connections stalls interactive traffic that would have been fine. Isolating critical traffic
into its own pool is a **bulkhead** — `resilience.md` owns bulkheads and their failure semantics; this
file owns the sizing arithmetic (§7.1) for whichever pools that partition produces.

## 8. Latency budgets

### 8.1 Objectives are stated at a percentile, never as an average

**Applies when** the workspace emits latency histograms. Every route class then carries a declared
objective as a **threshold at a percentile** (e.g. p95 and p99), following the SRE-book practice of
stating objectives distributionally. Prevents the mean hiding the incident: a healthy average is
routinely a fast majority plus a tail that is one customer's data volume. Declare objectives for **money
and availability paths first** (`observability.md` §3.1's alarm classes); elsewhere the profile may
record "no objective, because…", and an unrecorded absence is the finding — an objective nobody wrote
down cannot be violated.

### 8.2 A budget decomposes across the call graph, or it is fiction

A route's budget MUST be allocatable: its downstream call allowances (§7.2's acquire wait included) plus
its own compute MUST fit inside the number claimed. A 200 ms objective in front of three sequential 300
ms dependencies is a wish, and stating it makes the review pass that should have caught the design. The
*mechanic* of propagating the remaining budget and keeping inner deadlines shorter than outer is
`resilience.md` §2.2; this rule is the arithmetic being possible before anyone writes the constants.

### 8.3 Expired work is cancelled, not completed

When a request's deadline passes or its caller disconnects, in-flight work on its behalf MUST be
abandoned. Work whose result nobody will read consumes exactly the capacity needed to recover, which is
how a latency spike becomes a cascading failure rather than a blip (Google SRE Book, *Addressing
Cascading Failures*). Cancelling the in-flight query itself **applies when** the runtime and driver
expose cancellation; where they do not, the deadline still stops *new* downstream work and the gap is a
§9.1 waiver. Narrow exception: work already paid for, or mutating durable state, completes through its
own finalizer (`data-integrity.md`).

### 8.4 User-facing surfaces carry a client-side budget too

A backend that meets its budget can still ship an unusable surface. Web clients declare targets on the
current Core Web Vitals metric set — LCP, INP, CLS, each judged at the 75th percentile of real users —
and any polling client declares its interval against the server's rate budget (`resilience.md` §9 owns
client backpressure). **Applicability is a profile row:** which surfaces are held to which targets; a
recorded "this internal admin surface is exempt, because…" is a complete answer, an *unrecorded* one is
the finding.

## 9. Accepted gaps

### 9.1 A gap you accept is a dated waiver, not a silence

Several rules here are gated on facts a project may not have: no plan command (§2.5), no bounded
instance count (§7.1), no histogram pipeline (§8.1), no cancellable driver (§8.3), a route that cannot
yet stream (§5.3). Each accepted gap MUST appear as a **dated waiver with an expiry** in the register
the workspace already keeps — `supply-chain-and-build-integrity.md` §6.1 owns that mechanism and this
file adds no second one. Prevents the two ways a standard dies: silently ignored because one rule did
not fit, or routed around by a bespoke process. An unrecorded gap is worse than an expired one — nothing
surfaces it.

## Failure shapes

Named patterns from real audits, genericised. Recognise one, cite it by name.

- **The wedged claim.** A claim query sorts on an unindexed field over payload-laden records; correct
  and fast until the backlog crosses the store's in-memory sort budget, at which point every claim
  aborts and the pipeline stops permanently — during the peak that caused it. (§2.2, §5.1)
- **The invisible loop.** A handler that reads as one query issues one more per returned row through a
  lazily-resolved relation in a serializer. Three fixture rows, four queries, green suite; three
  thousand rows in production. (§3.2, §3.3)
- **The fat field that taxed everything.** One multi-MB payload embedded in a record makes every scan,
  sort, poll, and sweep on that collection expensive — including queries that never read the field, and
  the poll that fetches it only to discard it. (§5.1, §5.2)
- **The stampede at expiry.** A hot cached value with a uniform TTL expires for all viewers at once;
  every request regenerates it simultaneously and the origin takes its spike precisely when the cache
  stopped absorbing load. (§6.4)
- **The queue behind the metric.** Requests wait for a connection from an undersized pool;
  query-duration looks healthy because the slow part is the wait *before* the query — and the acquire
  wait is unmeasured and undeadlined. (§7.1, §7.2)

## Checklist

Each box is decidable from the diff **plus the profile**; two need a live plan or an infrastructure fact
and say so. Before merging a change that reads or writes data:

- [ ] Every new/changed query shape has a backing index declared beside it naming the query, covering
      the **sort** and not only the filter — and no new index lacks a consuming query?
- [ ] New query filters on a left-to-right **prefix** of an index in the profile's table, not a suffix?
      Any "this is indexed" claim reached without a plan labelled **inferred**? *(plan)*
- [ ] No per-item query inside a loop over a fetched list — every returned relation eagerly loaded or
      batched at the fetch site, with a query-count assertion in its test?
- [ ] Collection endpoint: limit in the query, declared over-max behaviour applied, cursor rather than
      deep offset? Background/sweeper/migration queries batched too?
- [ ] Reads projected to the fields used; no blob in a record a scan will touch; anything unbounded
      streamed rather than buffered; sort/aggregation pushed into the store within the
      blocking-operation budget the profile records?
- [ ] New cache entry: key includes the viewer/scope, TTL set and justified as a staleness bound (or
      immutability recorded), TTL jittered, invalidation on the write path?
- [ ] Cache write on a key the profile marks hot and expensive, with no single-flight, early expiry, or
      serve-stale? Cache emits hit/miss; pool emits acquire-wait with a timeout?
- [ ] New pool or connecting process: does the profile's fleet-wide sum still fit the server's limit?
      *(infrastructure fact)* Latency objective still adds up against its allowances?
- [ ] Any rule this change cannot satisfy carries a dated waiver (§9.1)?

## Guard rails

CI checks that make this enforceable rather than aspirational; judgement-only rules say so.

- **[performance-and-data-access.GR1]** **Explain-plan assertions in the test suite.** For each query shape in the profile, run the engine's
  plan command against a seeded database; assert the intended index is used and no blocking-sort stage
  appears. The only mechanical check that catches §2.2's cliff early.
- **[performance-and-data-access.GR2]** **Index-declaration drift check.** A startup or migration-test assertion that every index the code
  declares exists in the database, plus a check flagging declared indexes with no named consuming query
  (§2.1). A dropped index fails no type check.
- **[performance-and-data-access.GR3]** **Query-count assertions on collection endpoints** (§3.3) — most ORM/ODM stacks expose a query counter
  or logger hook; assert the count is constant across fixtures of 3 and 30 rows.
- **[performance-and-data-access.GR4]** **Bound lint on collection reads.** A lint rule (e.g. a custom ESLint rule or a Semgrep-class pattern)
  flagging a find/select without a limit or a stream in handler and worker paths. Coarse on purpose: a
  lint suppression carrying a reason is a reviewable decision a grep can inventory; anything outliving
  the change belongs in §9.1's register.
- **[performance-and-data-access.GR5]** **Response-size assertion** on routes with a declared ceiling, and a **load-shaped regression test**
  on money/availability paths — run the hot path against a production-sized fixture, asserting
  wall-clock and query count against a recorded baseline.
- **[performance-and-data-access.GR6]** **Judgement-only, stated as such:** no check decides whether a latency is *acceptable* (the profile
  supplies the objective, §8.1), and no linter knows a cache key omits the viewer — compensate with a
  test fetching one cached resource as two principals (§6.1).
