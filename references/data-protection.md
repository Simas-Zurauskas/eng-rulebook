# Data Protection Standard

> **Type:** Generic, reusable standard · **Rev:** 1 (2026-07-28)
> **Audience:** AI agents and humans writing or reviewing code.
> **Status:** Part of the eng-rulebook library, bundled in the `eng-rulebook` skill (references/).
> Loaded on demand via the skill's routing table (SKILL.md).
>
> Governs personal data as a *code* concern: what you collect, where it goes, how long it stays,
> and whether you can prove it is gone. Core idea: **every property a data-protection regime asks
> you to demonstrate is a property of your code and your schema — so it is testable, and if it is
> not tested you cannot claim it.**

## 0. Scope

Assumed context: a multi-repo TypeScript workspace — backend API, web client(s), mobile app,
worker(s) — with docs generated by wiki-system and client types code-generated from a runtime
API spec. Rules are stack-agnostic; technology names are labelled examples.

**Owns:** the personal-data inventory, retention by class, deletion and export *implementation*,
residency and cross-border transfer as a code constraint, egress to third parties
(sub-processors), pseudonymisation and minimisation at rest and in transit, consent as stored
state, and the regulatory-applicability record.

**Does not own** (one-line cross-refs only):

- Cascade *mechanics* — atomic multi-store deletes, loud partial failure → `data-integrity.md`.
- Log/report masking mechanics and PII-in-telemetry enforcement → `observability.md`.
- Storage access posture, bucket privacy, presigned URLs → `security.md` §9.
- Authentication, session revocation, and credential handling → `security.md` §2.
- What leaves your boundary to a model provider → `ai-features.md`.

**External anchors** — name + version + status, never URLs. *Anchors verified 2026-07-28;
re-verify anything older than 12 months (`_authoring.md` rule 6).*

**Applicability is never assumed.** This standard states properties that are good engineering for
any product holding personal data. *Which* regimes bind a given project is a **profile row**
(Appendix A), and a recorded "no, because…" is a complete answer. An **unrecorded** answer is the
finding. Nothing in this file asserts that any particular organisation is in scope for anything.

## 1. Core principle

A data-protection regime asks you to demonstrate four things: what you hold, why you hold it, how
long you hold it, and that you can stop holding it. Every one of those is a statement about your
schema and your code paths — not about a policy document.

That reframing is the whole standard. "We are compliant" is a claim about a PDF; **"account
deletion covers all eleven stores, asserted by a test that reads the inventory"** is a claim about
your repository, and an auditor can check it in one command. Where a regime's obligation cannot be
reduced to a property of the code, it is out of this library's lane and belongs to whoever owns
policy.

The consequence that catches teams: **the inventory is the load-bearing artifact.** Deletion,
retention, export and residency are all *derived* from knowing what you hold and where. A cascade
tested against a developer's memory of the schema passes on the day it is written and rots from
the next migration onward.

## 2. The personal-data inventory

### 2.1 Every store holding personal data is enumerated in the profile

One row per collection, table, bucket prefix, cache, queue payload shape, and third-party
destination. A store nobody wrote down is a store no deletion cascade covers and no retention
policy reaches — and it will be discovered during an incident, which is the worst time.

Include the stores people forget: search indexes, analytics pipelines, error-reporting payloads,
CDN caches of user content, backup snapshots, and message-queue payloads in flight.

### 2.2 Classify by sensitivity, because the rules differ by class

At minimum: **identifiers** (email, phone, account id), **content** (anything the user authored
or uploaded), **derived** (inferences, scores, embeddings), and **special category** where a
regime defines one. The class drives retention (§3), egress (§5) and pseudonymisation (§6) — a
single undifferentiated "PII" flag makes every later rule undecidable.

**Derived data is personal data.** An embedding, a risk score, or a model-generated summary
computed *from* someone's content is still about that person, and deletion that leaves the
derivation behind has not deleted anything meaningful.

### 2.3 The inventory is verified against the schema, not against memory

The profile's inventory MUST be reconcilable with what the code actually declares — model
definitions, migration files, bucket prefixes. A guard rail that diffs declared stores against
discovered ones (Guard rails) converts "we forgot to add the row" from a silent gap into a
failing check.

## 3. Retention

### 3.1 Every PII-bearing store declares a retention period

A TTL, a lifecycle rule, or an explicit **"kept until account deletion"** — recorded per row in
the inventory. *"We never decided"* is the finding, not a neutral state: undeclared retention
means the answer is "forever", chosen by nobody.

### 3.2 Retention is enforced by a mechanism, not by intention

A declared period with no TTL index, no lifecycle rule and no sweeper is a comment. Name the
enforcing mechanism in the inventory row. Where the mechanism is a scheduled job, its
missed-tick and overrun behaviour is `resilience.md`'s lane — cross-reference it rather than
restating.

### 3.3 Shorter retention for the noisiest classes

Logs, error reports and analytics events accumulate personal data incidentally and at volume, and
they are the stores least likely to appear in a deletion cascade. Give them the shortest
defensible retention and enforce it at the sink, not by hoping the emitter stayed clean
(`observability.md` owns masking at emit).

### 3.4 Backups have their own retention, stated separately

A backup that outlives the retention of the data inside it silently extends that retention.
Backups legitimately cannot support per-record deletion — so state the backup retention window,
state that deletions propagate by expiry rather than by cascade, and make the window a deliberate
number rather than an accident of the storage plan.

## 4. Deletion and export

### 4.1 Deletion is complete and provable

Account deletion covers every store in the inventory — records, sessions, refresh tokens, push
tokens, every storage prefix **including public or shared copies**, search indexes, derived
artifacts (§2.2), and deletable third-party artifacts. Cascade mechanics — atomicity and loud
partial failure — are `data-integrity.md`'s lane.

**The obligation this standard adds: the cascade is tested against the inventory, not against
memory.** The test enumerates the profile's stores and asserts each is empty for the deleted
subject. A cascade whose test hardcodes the store list passes forever after the twelfth store is
added.

### 4.2 Deletion means deleted, or the difference is declared

If a "deletion" is a soft-delete flag, an anonymisation, or a tombstone, say which — in the
inventory row and in the user-facing copy. A soft-delete presented as deletion is the gap most
likely to be discovered by someone else.

Where a record must survive deletion for a stated reason (a financial record, an audit trail),
that is a legitimate design — it is only a defect when it is **undeclared**. Name the store, the
reason, and what is stripped from it.

### 4.3 Export is an implemented path, not a manual query

Where a project owes data portability, the export path is code with a test — not an engineer
running a query. A manual export path is one holiday away from an unmet deadline, and it reliably
misses the same stores the deletion cascade misses.

### 4.4 Both paths are authenticated, authorised, and rate-limited

A deletion or export endpoint is a high-value target: one takes data out, the other destroys it.
Owner-scoped by the authenticated subject id in the query itself, and covered by the credential
budgets in `security.md` §8.

## 5. Egress — every third party is a store you do not control

### 5.1 Enumerate third-party destinations with what they receive

Analytics, error reporting, email and push providers, payment processors, model providers,
support tooling. Each is a row in the inventory with the **data classes it receives** — not just
a vendor name. "We send events to an analytics provider" is not an answer; "identifiers +
derived, no content" is.

### 5.2 Egress is opt-in per field, never per-object by default

Sending a whole object because it was convenient is how content and special-category data reach
a vendor contracted for identifiers. Serialise an explicit field list at the boundary. This is
the same parse-don't-assert discipline `type-safety.md` applies to inbound data, applied
outbound.

### 5.3 A third party's retention and deletion are yours to state

For each destination, record whether deletion propagates, how, and with what lag. Where a
provider offers no deletion path, that is a decision to record in the inventory, not a detail to
discover later.

## 6. Minimisation and pseudonymisation

### 6.1 Collect what the feature needs, not what might be useful

Every field collected becomes a field to retain, delete, export, and possibly disclose. Fields
added "in case we want to analyse it later" carry the full lifecycle cost for a benefit nobody
scheduled.

### 6.2 Separate identifiers from content where the join is not needed

Where a workload does not need to know *whose* data it processes — aggregate analytics, model
evaluation, most background processing — give it a pseudonymous key rather than the subject id.
The failure this prevents: a breach of a processing store becoming a breach of an identity store
because the two were never separated.

### 6.3 PII stays out of logs, error reports, analytics, and generated docs

`observability.md` owns the masking mechanics; the obligation here is that the **inventory names
which fields are PII**, so masking has a list to work from rather than a reviewer's judgement.

## 7. Residency and transfer

**Applies when:** the profile records a residency or transfer constraint.

### 7.1 Residency is a deployment fact, recorded per store

Region of every database, bucket, queue, cache and third-party destination — in the inventory.
A store whose region nobody recorded cannot be asserted to satisfy any residency claim.

### 7.2 A transfer constraint is enforced in configuration, not in a review

Where data must not leave a region, the enforcement is a bucket/region policy or an account-level
control — something that fails closed when misconfigured. A code review is not a residency
control: it catches the change that was reviewed.

## 8. Consent and lawful basis as stored state

**Applies when:** the profile records a regime that requires a lawful basis or consent.

### 8.1 Consent is a record, with a timestamp and a version

Not a boolean. Which purpose, which version of the notice, when, and through which surface —
because "did this user agree to this specific processing at the time it happened" is the actual
question, and a bare flag cannot answer it retroactively.

### 8.2 Withdrawal is as implemented as granting

A consent that can be given through the product and withdrawn only by emailing support is not
withdrawable in any operational sense. Withdrawal stops the processing it covers — which means
the processing path reads the consent record at consume time, not at signup.

### 8.3 Map fields to purposes in the profile

Each inventory row records **why** the field is held. This is the row that makes §6.1 decidable:
a field with no purpose is a field to remove.

## Failure shapes

Named patterns from real audits, genericised. Recognise one, cite it by name.

- **The forgotten store** — a deletion cascade covering the stores that existed when it was
  written, silently missing the search index, the analytics pipeline, and the two buckets added
  since. It passes its own test, because the test hardcodes the same list the cascade does. (§4.1)
- **The soft delete presented as deletion** — the record is flagged, the user is told it is gone,
  and nobody wrote down the difference. Discovered by someone external. (§4.2)
- **The whole-object egress** — a vendor contracted to receive identifiers receives user content
  because a convenient serialiser sent the whole object. Nothing failed; the data class simply
  changed silently. (§5.2)
- **Retention by omission** — no TTL, no lifecycle rule, no sweeper, and no decision anywhere.
  The effective retention is forever, chosen by nobody, and it is discovered when a store's size
  becomes an incident. (§3.1)
- **The immortal backup** — per-record deletion works perfectly in production and the data lives
  on for the backup window nobody stated, quietly extending every retention period in the
  inventory. (§3.4)
- **Consent as a boolean** — the flag says true, and no one can say to which notice version, for
  which purpose, or on what date, so no historical processing can be justified. (§8.1)

## Checklist

Before merging a change that touches personal data:

- [ ] New field or store holding personal data → inventory row added, with class and purpose?
- [ ] New store → retention declared **and** an enforcing mechanism named?
- [ ] New store → added to the deletion cascade **and** to the cascade's test fixture?
- [ ] New third-party destination → data classes it receives recorded, egress field-listed?
- [ ] Deletion still complete: does the diff add a derived artifact (index, embedding, cache)
      that now outlives the record it came from?
- [ ] Does the diff put a personal-data field into a log, error report, metric label, or
      generated doc?
- [ ] New consent-gated processing → reads the consent record at consume time?
- [ ] Residency constraint recorded → does the new store's region satisfy it?

## Guard rails

CI checks that make this standard enforceable, not aspirational:

- **[data-protection.GR1]** **Inventory reconciliation** — a check that diffs the profile's declared stores against the
  stores discoverable in code (model/schema declarations, bucket prefixes, migration files) and
  fails on an undeclared one. This is the single highest-value check here, because §3, §4, §5 and
  §7 all derive from the inventory being complete.
- **[data-protection.GR2]** **Deletion-cascade test driven by the inventory** — the test enumerates the profile's stores
  rather than a hardcoded list, so adding a store without adding it to the cascade turns the
  cascade test red. A cascade test with a literal store list is the failure shape, not the check.
- **[data-protection.GR3]** **Retention declared** — a check that every inventory row has a non-empty retention and a named
  mechanism; empty cells fail.
- **[data-protection.GR4]** **PII-in-telemetry scan** — a pattern check over log/metric/report call sites for the field
  names the inventory marks as PII (`observability.md` owns the masking implementation).
- **[data-protection.GR5]** **Egress field-list assertion** — a test per third-party destination asserting the serialised
  payload contains exactly the declared fields, so a model gaining a field does not silently
  widen what a vendor receives.
- **[data-protection.GR6]** **Judgement-only, and stated as such:** whether a purpose is legitimate, whether a retention
  period is proportionate, and whether a regime applies are **not** mechanizable. They are
  profile decisions with a recorded owner and a review date; no check here substitutes for them.
